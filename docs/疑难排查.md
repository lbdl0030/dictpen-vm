# 疑难排查

> 这份文档**只讲现象**：卡住了，就按"你看到了什么"往下查。每条都是「现象 → 判定 → 根因 → 修法 → 出处」，能落到命令或字段。
> **机制**（宿主与四个插件点的接口、生命周期、失败表现）看 `docs/插件模型.md`；写包的步骤看 `docs/固件包开发教程.md`。
> 带 `vm/` 的路径是**本机工作记录，不进版本库**（`.gitignore` 排除）；长期有效的证据要落到包内 `README.md` / `DEVLOG.md`。

## 0. 先取证（通用手段）

任何一条排查，先做三件事：看串口、看 guest 日志、看截图**字节数**。

**串口日志** `vm/serial.log`（每次开机 chardev 重写，只含本次引导）；QEMU 自身输出在 `vm/qemu.log`。搜这几行先确认框架这一侧的适配生效：

| 串口里搜 | 含义 |
|---|---|
| `### pack: <名> runtime=<runtime> panel=<WxH> ###` | 包已生效、面板尺寸已带上 |
| `### <ext4\|erofs> root mounted ###` | 镜像格式对 |
| `### state: ext4 created and mounted ###`、`### overlay: persistent upper ###` | 状态盘 / 可写根就位（否则见 §7.5） |
| `### switch_root -> /mnt, init /sbin/init ###` | 已交棒给固件自己的 init |
| `overlayfs: failed to create directory /state/work/work (errno: 28)` / `Read-only file system` | 状态盘满、overlay 退化只读（§7.1） |
| `S00license: dev license written` | 开发凭证已写入（§5.1） |

**guest 日志**（都在 guest 里，用 `dpctl sh` 取）：`/userdata/applog/DictPen_*.log`（应用日志，a6/a7 一族）、`/userdata/applog/vm-miniapp.log` 与 `vm-weston.log`（x6pro 一族，`S50vm-ui` 起）、`/userdata/applog/Capframe_*.log`、`/userdata/applog/wifimgr.log`、`/tmp/touchbridge.log`（要 `TOUCHBRIDGE_DEBUG=1`）、`/tmp/adbd.log`、`/userdisk/corefile/<版本>/miniapp-*.dmp`（Breakpad dump）。

**`dpctl sh` 常用判据**（先跑一遍，多数现象当场分流）：

```bat
python scripts\dpctl.py sh -c "ps | grep miniapp"
python scripts\dpctl.py sh -c "grep -c 'could not load module' /userdata/applog/DictPen_*.log"
python scripts\dpctl.py sh -c "grep -c 'launchApp fail'      /userdata/applog/DictPen_*.log"
python scripts\dpctl.py sh -c "ls -l /dev/fb0; df -h /state; ls /userdisk/corefile | wc -l"
python scripts\dpctl.py sh -c "cat /sys/class/power_supply/battery/capacity"      :: 期望 80
```

**截图按字节数分类**（`dpctl screenshot` 出来的 PNG）——先分类，再查对应那条：

| 字节数 | 含义 | 往哪查 |
|---|---|---|
| ≈400（640×172 全 0） | **一个字都没画** | §1 的加载链 / HAL |
| 几十~一百多 KB、但被裁或大片黑 | **画了，版式不对** | §1 的主题 / 尺寸 |
| 100 KB 以上（640×172 ≈107 KB；960×266 / 800×254 ≈200 KB） | 桌面 / 整帧 | 正常；要做点击看 §2 |

## 1. 画面：全黑 / 花屏 / 斜切 / 被裁

### 1.1 全黑，截图 ≈400 B，`could not load module` / `launchApp fail` 非 0
- **判定**：`dpctl sh -c "grep -c 'could not load module' /userdata/applog/DictPen_*.log"` 与 `… 'launchApp fail' …` 两个计数非 0 = 框架的 JS/jsapi 链断在加载阶段。
- **根因**：包的 `patches/runDictPen.sh` 替代厂商 `/usr/bin/runDictPen` 时漏了 `LD_LIBRARY_PATH` 的 `/etc/miniapp/jsapis` 与 `/etc/miniapp/messageknife` 两段 → `libjsapi_export_core.so` 的 `DT_NEEDED` `libgetdevicename.so` 找不到（它只在 `messageknife/`）→ uClibc `dlopen` 失败（日志 `ERROR:File not found:dlopen in dynamic_load_jsapi`，`File not found` 就是 `dlerror()`）→ `global` jsapi 加载不了 → `globalManager-*.js` / `app.js` 连败 → `$falcon.launchApp` 抛 `TypeError: not a function` → 框架退回启动「验证引导」(8080282888534774)，它不画东西 → 全黑。
- **修法**：把两段补回去，厂商原版是 `export LD_LIBRARY_PATH=$APP_PATH/libs:$LD_LIBRARY_PATH:/etc/miniapp/jsapis:/etc/miniapp/messageknife`。不重启也能验：`killall -9 guardian_run miniapp runCapFrame` 后用正确路径手工起 `/usr/bin/miniapp`，截图应从 400 B 变 ~100 KB。
- **出处**：`packs/a7pro/README.md#黑屏的真正原因2026-10-01-修复rundictpen-替代脚本漏了库搜索路径`；`packs/x5pro/README.md` §9；`vm/_a7pro-verify/FINDINGS.md` §7（未入库）。对照包选**同族能出画面**的 a6pro（两个计数都是 0、第二个 app 直接是 HOME `8080222437664451`）。

### 1.2 全黑，miniapp 反复重启（pid 每几秒变一次），corefile 却不增
- **判定**：`pidof miniapp` 有值但 pid 每几秒变；`vm-miniapp.log` 反复刷 `start /usr/bin/miniapp`；`ls /userdisk/corefile/4.3.5/` 数量不变（是 abort，Breakpad 不落 dump）。前台跑一次得 `EXIT=134`（SIGABRT），gdb 栈是 `greenui::NativeWindow::create ← WindowManager::getNativeWindow ← falcon_entry`（建窗口失败）。
- **根因**：合成器没起来。`/run` 在 overlay 的 upper（状态盘）上、**不随重启清空**，硬断电会留下 `/run/debweston/wayland-0`；而 `S50vm-ui` 的守卫是 `[ ! -S "$XDG_RUNTIME_DIR/wayland-0" ]`，stale socket **照样通过 `-S`** → 合成器被永久跳过 → 应用连不上 wayland，`NativeWindow::create()` 每次 abort。
- **修法**（`patches/S50vm-ui`）：守卫改看进程，并在启动前清残留——`if ! pidof weston >/dev/null 2>&1; then rm -f "$XDG_RUNTIME_DIR/wayland-0" "$XDG_RUNTIME_DIR/wayland-0.lock"`。判据：`pidof weston` 有值、`wayland-0` 时间戳是本次开机的。
- **出处**：`packs/x6pro/DEVLOG.md` §5.6(2)、§7。

### 1.3 全黑，合成器日志每条输出都是 `Failed to init output pixman state`
- **判定**：`dpctl sh --serial -c "tail -3 /userdata/applog/vm-weston.log"`——能枚举 EDID、能发现 head，但每条输出都停在 `Failed to init output pixman state`；固件里有 `librga.so.2` / `libmali.so.1` 字样、`/etc/profile.d/pixman.sh` 里 `PIXMAN_USE_RGA=1`。
- **根因**：厂商合成路径两条腿都在 Rockchip 专有硬件上——GL 要 Mali（`/dev/mali`）、pixman 要 RGA（`/dev/rga`）；QEMU 上两者都不存在，厂商 Weston **没有软件路径**。
- **修法**（全在包内）：换 Debian bookworm arm64 的 **Weston 10 + Mesa libgbm + pixman** 纯软件合成（载荷 `weston.tar` → `S50vm-ui` 解包并启动）。三个必踩点：载荷必须含 `weston/libexec_weston.so.0`（漏了合成器静默不启动）；必须 `--tty=1`（无 logind，走 direct launcher 才拿得到 DRM master）；socket 固定 `--socket=wayland-0`。**库隔离**：合成器走自己的 `LD_LIBRARY_PATH`，应用只用固件自己的库，混用会让应用加载到 Debian 的 `libfreetype` 而缺 `libbrotlidec.so.1`。
- **出处**：`packs/x6pro/DEVLOG.md` §3。

### 1.4 `fb0` 里有内容，截图却全黑
- **判定**：`dd if=/dev/urandom of=/dev/fb0` → 截图有噪声（说明 fb0 → QEMU 扫描整条链路通、偏移/bpp 全对）；`od` 看 fb0 像素是 `ff000000` 整屏。
- **根因**：应用在画**不透明黑底**（splash）——"画了但没内容"；多数是 §1.1 的 jsapi 断链后停在「验证引导」（它不画内容）。
- **修法**：按 §1.1 修加载链，桌面即出。
- **出处**：`packs/s7pro/README.md` §5。

### 1.5 全黑 / 停在启动图，`/dev/fb0` 不存在
- **判定**：`dpctl sh -c "ls -l /dev/fb0"`；串口搜 `mod:` 行。
- **根因**：显示模块没加载。需要 `ttm` / `drm_ttm_helper` / `drm_vram_helper` / `bochs` **全部 ok**，且用的是 **bochs-display**（不是 virtio-gpu）。
- **修法**：确认包在 `[display]` 声明了尺寸（EDID 由它现算）。virtio-gpu 下"永远停在启动图"是**预期的**——falcon 不做 flush，别往这条线上查。
- **出处**：`README.md#已知问题排查`。

### 1.6 斜切 / 斜条 / 上下颠倒 / 颜色不对，或 `fbdev: Failed to setup generic emulation`、`dbuffer=false` 变黑
- **判定**：串口搜 `cfg.json: applied N override(s) from the pack`；看 guest `/etc/miniapp/resources/cfg.json` 的 `direction` / `width` / `height` / `bpp` / `dbuffer`。
- **根因**：`direction` 不是 0（falcon 按旋转后的跨度写）、显示模式不是面板尺寸、`bpp` 不是 32；`fbdev: Failed to setup generic emulation` 是 DRM 的 dumb 创建参数被改坏；这台 app 走**双缓冲**，`dbuffer=false` 就彻底黑屏。
- **修法**：`cfg_overlay` 把 `width/height/direction` 归一化到与 `[display]` 同一坐标系（常见 `direction=0` + 横屏尺寸、`bpp=32`、`dbuffer=true`）；**勿改 pitch 计算**（会连 fbdev 一起挂），对照能出画面的同族包 diff。
- **出处**：`README.md#已知问题排查`；`packs/x5pro/README.md` §5、§6.7；`packs/s7pro/README.md` §3；`docs/固件包开发教程.md` §6.1。

### 1.7 被裁（几十~百多 KB，但右边/下边少一块）
- **判定**：`dpctl sh -c "cat /userdata/miniapp/resources/env.json"` 看 `theme` / `currentScreenWidth` / `currentScreenHeight`；应用日志搜 `loadRootPage themeName=`。a7pro 正常是 `640 / 172 / theme-y09`，坏时是 `960 / 266 / theme-melon`。
- **根因**：机型码来自 vendor storage，VM 里没有 `/dev/vendor_storage` → 主题查表 miss → 回退到固件常量 `MOCK_THEME = "theme-melon"`，而 melon 按 **960×266** 排版，1:1 画进 640×172 就被裁（实测把 960×266 渲染裁左上角与 640×172 截图逐像素比，差异 0%）。
- **修法**：包内 `runDictPen.sh` 钉一行 `export MOCK_THEME=theme-y09`（`themeName()` 第一件事就是读 `YEnvironment::value("MOCK_THEME","")`，非空直接用、不再查表）。面板尺寸本身从真机 `/etc/miniapp/resources/cfg.json` 的 `width/height` 取；想更彻底见 §5.5。
- **出处**：`packs/a7pro/README.md#画面分辨率为什么对不上2026-10-02-修复`；`docs/固件包开发教程.md` §6.1。

## 2. 触摸：点了没反应 / 只能点一下 / 滑不动

### 2.1 点击完全没反应，且状态盘满 / 输入服务崩溃循环
- **判定**：`dpctl sh -c "df -h /state"`；`ls /userdisk/corefile | wc -l`（正常 ≤ 500，实测曾到 27877）；日志里 `No space left on device`。
- **根因**：`CapFrame` / `run_input_event_monitor` 每秒写崩溃日志，把盘顶满 → 输入子系统已经死了，点击必然没反应（**不是**触摸桥的问题）。
- **修法**：见 §7.1 / §7.2；先排除这一条，再去查桥。
- **出处**：`README.md#已知问题排查`；`packs/s7pro/README.md` §8。

### 2.2 `dpctl tap` 报连接被拒 / `WinError 10061`，但 `screenshot` 正常
- **根因**：vmgui 在前台，长期占着 QMP 4446；**QEMU 的一个 QMP chardev 只服务一个客户端**。`screenshot` 走 HMP 4445 不受影响——"截图正常但 tap 失败"是占用，不是 VM 挂了。
- **修法**：先关 vmgui 窗口，或用 `up --display none` / `--display gtk` 起。
- **出处**：`packs/x6pro/DEVLOG.md` §5.9、§7；`docs/使用手册.md` §12。

### 2.3 点、滑都不通：桥创建的 uinput 设备能力位是空的
- **判定**：桥日志的 `down/move/up` 齐全，但设备属性是 `B: EV=1`（只有 `EV_SYN`）、没有 `B: ABS` 行——`EV=1` 就是 `input_allocate_device()` 的初始状态，**一个位都没设上**。
- **根因**：内核的 `UI_SET_EVBIT/KEYBIT/ABSBIT/PROPBIT` 参数是**位号本身**（按值传）；Perl 的 `ioctl` 第三参给字符串时传的是**缓冲区地址**，内核把地址当位号 → 一律 `EINVAL`。而 `UI_DEV_SETUP/UI_ABS_SETUP/UI_SET_PHYS` 确实要指针——两类混在同一脚本里，不检查返回值的那些失败就看不出来。
- **修法**：桥的 `setbit()` 统一按值传参。修好后应是 `B: PROP=2`、`B: EV=b`、`B: KEY=400 0 …`、`B: ABS=3`，weston 记 `event2 - axs_ts: is tagged by udev as: Touchscreen`。
- **出处**：`packs/x6pro/DEVLOG.md` §5.6(1)、§7（桥的三条脚本层规则见 `docs/固件包开发教程.md` §6.2）。

### 2.4 点能用（或也不能用），滑动全废
- **判定**：桥日志 `down` 有、`N×move` 与 `up` 也有，界面就是不动；用 `evtest /dev/input/event1`（**不加 `--grab`**，可与桥并行读）抓源设备：**`BTN_LEFT` 按下那一帧里没有 ABS**。
- **根因**：QEMU 的 input 核心对"没变化的绝对轴"**去重**——`dpctl tap` 的四批事件用同一组坐标，带 `BTN_LEFT` 的那批已经没有 ABS 了；桥若写"本帧收到坐标才动手"（`next unless $seen`），按下/抬起帧就被吞。**坐标是状态，不是边沿。**
- **修法**：位置常驻状态，每个 SYN 帧都算一次 `px,py`，只按 `BTN_LEFT`/`down` 组合决策：`!btn && down` → 发 `BTN_TOUCH 0`；`btn && !down` → 用**最近一次已知位置**发 `BTN_TOUCH 1 + ABS`；移动只在位置变了时发 `ABS`。`rx/ry` 初值给面板中心（16383），避免第一次按下落在 (0,0)。
- **出处**：`packs/x6pro/DEVLOG.md` §5.8、§7。

### 2.5 落点偏移：越靠右偏得越多（右边缘约 12%）
- **判定**：`TOUCHBRIDGE_DEBUG=1` 看桥转发出去的坐标——`dpctl tap 500 100` 桥转发 ~`(437, 99)`（应为 `(499, 99)`）。
- **根因**：`patches/touchbridge.pl` 把面板尺寸**写死成 560×170**（a6pro 的面板）；UI 按 640×172 换算，X 被整体压缩 560/640。三份 `touchbridge.pl` 原本是同一个文件、同一哈希，a6pro 的常量因此被抄到了所有机型上。
- **修法**：尺寸改成"读"：第 3 个命令行参数 `WxH` > 环境变量 `TOUCHBRIDGE_PANEL` > guest 的 `/etc/miniapp/resources/cfg.json` 的 `screen.width/height` > 全取不到才回退 560×170 并告警。启动日志写明来源 `touchbridge: panel 640x172 (from /etc/miniapp/resources/cfg.json)`。
- **出处**：`packs/a7pro/README.md#触控偏移2026-10-02-修复触摸桥的面板尺寸是硬编码的`。

### 2.6 派发坐标恒 `(0,0)`，链路却看着正常
- **判定**：把 zlog 提级 DEBUG（`zlog_miniapp.conf` 的 `*.WARN`→`*.DEBUG`），看到 `FBNativeWindow::dispatchTouchEvent action=1, x=0.000000, y=0.000000`（tap 时序精确、坐标恒 0）。
- **根因**：桥重启会销毁它自己创建的 uinput 设备，而 app 的 fd 仍指向那个已销毁的节点，读不到事件——看起来像"坐标又坏了"。
- **修法**：验证脚本一律"**先起桥、再重启 app**"。
- **出处**：`packs/x5pro/README.md` §6.7「踩过的坑」；`packs/x6pro/DEVLOG.md` §7。

### 2.7 每次点击派发两条 DOWN，其中一条 `(0,0)` → 手势触发 + SEGV
- **判定**：日志里同一次点击有两条 DOWN（一条坐标正确、一条在 `(0,0)`），随后 `LeftSwipeBackGesture Start` → `Segmentation fault`。
- **根因**：app 同时读 `cfg` 的 `device.mouse`（mousedev 增量累加，光标初值在屏幕中心）与 `device.tp`；mouse 链每次点击注入一条假 DOWN `(0,0)`，落在屏幕左缘触发 `LeftSwipeBackGesture`/`TopSwipeGesture`。
- **修法**：把 `device.mouse` 置空（只剩 TP 一条链，派发变干净的 `action=1 → 3 → 2`）。框架覆盖表**表达不了空字符串**（值只有"数字 / 以 `/` 开头 / `true|false`"三类），要在包内钩子里 `sed` 补一次。
- **出处**：`packs/x5pro/README.md` §6.7「根因二」。

### 2.8 落点镜像 / 翻转
- **判定**：面板 800×254、桥上报 UI 像素时，`dir=0` 点 `(100,60)` 派发 `(100,60)`；`dir=180` 同点派发 `(699,193)` = (799−100, 253−60)。
- **根因**：`tp_direction` 与桥上报的坐标系不配套（桥报 UI 像素坐标，应用再按 `tp_direction` 变换）。
- **修法**：`tp_direction=0`（`tp_xoffset/tp_yoffset=0`）；桥不要自己猜应用的变换。
- **出处**：`packs/x5pro/README.md` §6.7「根因一」；`docs/固件包开发教程.md` §6.2。

### 2.9 "裸 tablet / 直接吃 BTN_LEFT"这套方案不成立
- **判定**：有些固件的 app 走 **tslib**（等 `EV_ABS/ABS_X,ABS_Y` + `EV_KEY/BTN_TOUCH`）；宿主 `tap` 抓包只有 `EV_KEY/BTN_LEFT` + SYN，没有 BTN_TOUCH、没有 ABS。
- **根因**：QEMU 的输入路由里 `key` 类型（BTN_TOUCH 330 是这么发的）落到 keyboard、`abs` 同样被丢，只有 `btn`（BTN_LEFT）真的到达 tablet。**触摸语义只能在 guest 内由桥合成。**
- **修法**：必须有 `touchbridge` 把 tablet 的 BTN_LEFT+ABS 重发布成 `BTN_TOUCH` 触摸屏，并把 `cfg` 的 `tp` 指向它（桥要在 app 之前就位）。
- **出处**：`packs/s7pro/README.md` §6；`packs/x6pro/DEVLOG.md` §5.8、§7。

## 3. 联网：网络明明通，UI 却说"需要联网"

### 3.1 `eth0`/`wlan0` 通着，`isOnline()` 却恒 false（含 Wi-Fi 开关卡在"正在开启/关闭…"）
- **判定**：`read -r s < /dev/bes2600; echo $s` 期望 `wifi opend`——`ls /dev/bes2600` 报 `No such file` 就是这条；`ps w | grep -E 'wifi-manag|bes2600' | grep -v grep`；`wpa_cli -iwlan0 status | grep -E 'ssid|wpa_state'`（应 `COMPLETED`）；应用日志 `wifiConnectedOperateResult====> global.isOnline(): false`。
- **根因**：应用的"联网"**不是可达性判断**，是厂商 wifi 状态机**推给 JS 的状态**（`wifi-manager` → D-Bus → `JSWifiProxy::onWifiStatusChanged` → `global.isOnline()`）。`cat /dev/bes2600` 失败 → wifi-manager 认定芯片 disabled → 永不发布 connected；eth0 通着也可能恒 false。
- **修法**（`patches/S45vm-wifi`）：用普通文件模拟 `/dev/bes2600` + **0.1 s** 循环把"命令"翻成"状态"回写（写 `cmd:WIFI_ON` → 回 `wifi opend`，`WIFI_OFF` → `wifi closed`，其余补 `wifi opend`；循环用内建 `read -r s < 文件`，别用 `$(cat 文件)`）；wpa_supplicant 配置搬到 `/data/cfg/wpa_supplicant.conf`（`/data`→`userdata` 软链）且 `update_config=1`；关联拿到租约后 `setsid /usr/bin/runWifiMgr &`。验证：首页状态栏出 Wi-Fi 图标、设置 → Wi-Fi 显示「已连接」、有道小P 卡片进云端页而非「此功能需要联网使用」。
- **出处**：`packs/x6pro/DEVLOG.md` §5.7、§7；`packs/x5pro/README.md` §8.1。

### 3.2 网络**真的**不通（`eth0` 没 IP / hostfwd 目标不存在）
- **判定**：guest 里 `ip addr` 无 eth0（连 UP 标志都没有）；串口有 `Bad system call`（SIGSYS）；宿主 `dpctl status` 的 ssh/adb "open 却连不上"。
- **根因**：vendor 的 dhcpcd（9.4.0）其 seccomp 白名单在 VM 的 Debian 6.1 内核上触发 SIGSYS 直接死，eth0 起不来。
- **修法**：装 `S00net-up`（`ifconfig eth0 up` + busybox `udhcpc` 配 vendor 自带的 `default.script`）。验证：串口 `S00net-up: dhcp lease ok`、`ifconfig eth0` 有 `inet addr:10.0.2.15`。
- **出处**：`packs/s7pro/README.md` §7。

### 3.3 排查方向：先找状态提供方，别调路由/DNS
- **判定**：应用能发 HTTP（日志有正常 JSON 响应）但 `isOnline()` 仍是 false。
- **结论**：这类固件的联网判定是**服务推给 JS 的状态**——先找 `isOnline` / `onXxxChanged` 这些 push 接口的**提供方**（`strings <厂商服务>` 里 `get_bes2600_state` / `set_bes2600_state` 这类字样），而不是继续调路由与 DNS。
- **出处**：`packs/x6pro/DEVLOG.md` §7；`packs/x5pro/README.md` §8.1。

## 4. 首启：卡在"正在初始化配置"

### 4.1 首启停在自带 splash「正在初始化配置，请等待…」
- **判定**：用**事件**判定，不要用固定时长——`dpctl sh -c "grep -c homeModeIconShow=false /userdata/applog/vm-miniapp.log"` ≥1；`dpctl sh -c "grep -c systemEnvCustomPresetAppInstalled /userdata/applog/vm-miniapp.log"` ≥1；`dpctl screenshot` >100 KB = 首页。
- **根因**：**不是挂起，是慢**。首启要把 `/etc/miniapp/resources/presetpkgs/*.amr` 的 35 个预设包（165 MB）逐个解到 `/userdisk`（TCG 下约 3 分钟），期间界面**一直是 splash**；装完应用会**主动重启**一次（日志 `home=systemEnvCustomPresetAppInstalled===restartMiniapp` → `~~~_exit`），随后才进首页。三次全新盘实测 373 s / 382 s / ~6–7 min，**全部**出首页。
- **修法**：等够 6~7 分钟再看；期间 pid 一定会变一次，别当崩溃。`userdata-seed.tar`（用一台已做完首启的机器的 `/userdata`+`/userdisk/miniapp`）是**可选加速**，不是必需闭合手段。
- **出处**：`packs/x6pro/DEVLOG.md` §5.10（推翻了 §5.1/§5.2 的旧结论"不完成"）。

### 4.2 首启期间偶发一次重启 + 一个 dump
- **判定**：`ls /userdisk/corefile/<版本>/miniapp-*.dmp`（约 370 KB）；宿主侧纯标准库解析 `python vm\_x6pro\dmpinfo.py <dump>`，看崩溃 PC `libydhal_devices.so + 0xa394`。
- **根因**：固件自己 `libydhal_devices.so` 里内联的 `FD_SET` 对未初始化的 fd 做越界读（索引 `0x64892`，等价 fd ≈ 2600 万）——读的是**未初始化栈内存**，每次开机垃圾值不同，于是时崩时不崩。
- **修法**：**不修**（固件自己的 bug，只在设备枚举不全的环境可达）；它**自愈**——guardian 重启后的下一个实例照常装包进首页，代价只是那次重启 + 一个 dump。
- **出处**：`packs/x6pro/DEVLOG.md` §5.10「附带查清」。

### 4.3 首启装完后状态盘就 67%
- **判定**：`dpctl sh -c "df -h /state"`（512 MiB 默认盘实测占 318/488 MB）。
- **根因**：35 个预设包解到 `/userdisk`，而 overlay 的 upper 也在同一块盘上。
- **修法**：包内 `[state] size_mb = 1024`——**只在创建时生效**（`up --fresh`，或删掉 `vm/state-<名>.img` 后 `up`）。
- **出处**：`packs/x6pro/DEVLOG.md` §5.10；`packs/a7pro/README.md#两个已修复的问题`。

## 5. 激活：停在激活/登录页

### 5.1 一直停在"开始激活"页
- **判定**：`dpctl sh -c "ls -l /userdata/cfg/license"` 不存在。
- **根因**：`/userdata/cfg/license` 没写进去（`S00license` 没跑，或被 `--no-license` 关掉了）。
- **修法**：去掉 `--no-license` 重起；确认串口有 `S00license: dev license written`。
- **出处**：`README.md#已知问题排查`；`docs/使用手册.md` §10。

### 5.2 用几分钟后自己跳到「验证引导」，笔用不了
- **判定**：前台 app 切到 `8080282888534774`；日志 `console(8080222437664451): ------- global.verifyLicense  false redo verify`；`grep -c -E 'redo verify|verifyLicense' <本次 DictPen_*.log>` 非 0（修复前约 5 分钟必触发）。
- **根因**：JS 侧 `global.verifyLicense` 会**重新校验**许可，失败就自己导航到「验证引导」——同 §5.3。
- **修法**：`patches/libydhal_devices.so` + `[adapt.replace]`，让 `yd_hal_verify_license` 恒真（只改一个 32 位字：文件偏移 `0x8f84`、`03 00 a0 e1` → `01 00 a0 e3`）。**固件版本一变必须重新生成**（脚本会先核对原字，对不上就拒绝改写）。验证：`redo verify|verifyLicense` 计数归 0；前台只切到 `8080252464522508 → 8080222437664451`(HOME)。
- **出处**：`packs/a7pro/README.md#用一段时间后提示激活笔用不了2026-10-02-修复`。

### 5.3 启动日志出现 `license verify failed`
- **判定**：串口/日志 `YStartupModulePrivate::initSecondaryStartupSignal license verify failed`，紧跟 `get_sn failed, sn len is 0` / `get_uuid error` / `vendor_storage open fail`。
- **根因**：这台固件做**真实的凭证校验**：凭证是 RSA 签名 + 设备绑定，设备码要从 `vendor storage` / `/proc/cpuinfo` 的 `Serial` / `/sys/class/block/*/device/cid` 取——VM 里这三样都没有（实测 `/dev/vendor_storage` 不存在、cpuinfo 无 `Serial`、`/sys/class/block/vda/device/` 无 `cid`），所以框架写的 174 字节开发凭证不可能通过。
- **修法**：开发 VM 里唯一稳的是 §5.2 的恒真补丁（开发绕过，不是"让凭证通过校验"）；要真凭证得拿**已注册设备**的 `system_info.bin`。
- **出处**：`packs/a7pro/README.md#开发凭证校验为什么过不了与黑屏无关`；`vm/_a7pro-verify/FINDINGS.md` §2（未入库）。

### 5.4 往 `system_info.bin` 写了 SN/UUID，重启却被抹掉
- **判定**：预置合法 SN/UUID 后重启，`strings /userdata/cfg/system_info.bin` 里 SN/UUID 又变空、`screen` 回到厂商的 `800*254`。
- **根因**：应用每次启动都**无条件**把整份 400 字节记录写回（`libyddal_adapter_core.so` `0x4b84c` 调 `file_utils::write_to_file(record, 400, path)`，三个 getter 失败只打日志、不阻止写入）；且 a7pro 的 UUID 根本不从该文件取（`get_uuid` 读 cpuinfo Serial 与 eMMC CID）。
- **修法**：这条路**结构性无效**，别在上面花时间；要么走 §5.2，要么让 getter 拿到真设备码（见 §5.5）。写盘槽位布局（400 字节，SN 在 `0x16`、UUID 在 `0x100`）见 a7pro README。
- **出处**：`vm/_a7pro-verify/FINDINGS.md` §2、§3（未入库）。

### 5.5 想让机型真被识别（而不是靠 `MOCK_THEME`）
- **判定**：`env.json` 的 `theme`/`currentScreenWidth` 走回退值（`theme-melon` / 960×266）而不是本机主题。
- **根因**：`/dev/vendor_storage` 不存在 → 机型码拿不到 → `themeName()` 落到常量 `MOCK_THEME`。
- **修法**：① 最快是钉 `export MOCK_THEME=theme-y09`（只解决 UI 尺寸）；② 彻底修要伪造 vendor storage：`rkvendor_read(id=0xE, buf, 0x400)` 返回 ASCII `<前缀>_<机型>_SKU_<区域>_<硬件档>`（`Y09` → serial `0x1e` → 机型表索引 `0x1e` = `YDPA7-1`），可替身 `libvendor_storage.so`（只导出 `rkvendor_read`/`rkvendor_write`）经 `[adapt.replace]` 覆盖。注意往 `/userdata/cfg/sys_config.conf` 写 `sku=` **没用**（应用启动就把它抹成空）。
- **出处**：`packs/a7pro/README.md#画面分辨率为什么对不上2026-10-02-修复`。

## 6. 远程：SSH 连不上 / adb 连不上

### 6.1 刚 `up` 完 ssh 就拒绝/超时
- **判定**：`dpctl status` 端口 open 但连不上。
- **根因**：dropbear 由 inittab 的 sysinit 启动，需要约 30 s。
- **修法**：等 30 秒再试；或直接用 `python scripts\dpctl.py wait`（会等到真正就绪）。
- **出处**：`README.md#已知问题排查`。

### 6.2 交互式 ssh 报 `PTY allocation request failed on channel 0`（退出码 255）
- **判定**：`grep pts /proc/mounts` 为空；`/dev/pts` 是空目录；登进去 `tty` 给不出 `/dev/pts/N`。故障只在**交互式**客户端（双击 `ssh-vm.cmd`、`-tt`、VSCode、Termius——不带远程命令）上出现。
- **根因**：固件自己的 userspace 从不分配伪终端，启动序列里没有挂 `devpts`；框架 initramfs 也只挂了 proc / sysfs / devtmpfs。dropbear 收到 PTY 请求后 `openpty()` 失败 → 拒绝 → 会话以 255 结束。**"带命令的 ssh"不要 PTY**，所以 `dpctl sh` / `guest_run` / initramfs 钩子一直好使——这就是"你全绿、用户全红"的分叉点。
- **修法**（框架级）：`scripts/initramfs-init.sh` 在 `mount -t devtmpfs none /dev` 之后补 `mkdir -p /dev/pts && mount -t devpts devpts /dev/pts 2>/dev/null || true`；`mount --move /dev` 会把子挂载一起搬进真根，所以一处修完全部机型。**改完必须 `python scripts\build-initramfs.py`**——每包 initrd 的缓存指纹记的是 base initramfs 的 md5（`packlib.ensure_initrd`）。
- **出处**：`packs/x6pro/DEVLOG.md` §5.9、§7；`docs/使用手册.md` §7.1。
- **判据纪律**：`dpctl sh` 只回传 stdout，**ssh 的警告全在 stderr 被吞**（`guest_run` 只在 rc==255 且命中 `SSH_TRANSPORT_ERRORS` 时才看 stderr），所以"`dpctl sh` 正常"**不能**当作"ssh 通道健康"的证据；判断通道要包含一次**不带远程命令**的交互登录。

### 6.3 `REMOTE HOST IDENTIFICATION HAS CHANGED!` / `Offending RSA key in NUL:1`
- **判定**：警告里出现 `NUL`。Git-Bash/MSYS 的 `/usr/bin/ssh` 不认 Windows 空设备名 `NUL`，会在**当前工作目录建一个真文件叫 `NUL`** 当 known_hosts；所有包共用 2222、每个型号一把 dropbear 密钥 → 换包必刷。
- **根因**：旧的 `-o UserKnownHostsFile=NUL` 写法。`StrictHostKeyChecking=no` **挡不住**这段（它只是照样放行），还会顺手禁掉密码/键盘交互认证。
- **修法**：统一指向真实文件 `vm/known_hosts_devvm`（`dpctl`、`ssh-vm.cmd`、`~/.ssh/config` 三处），`dpctl up` 每次开机清空；仓库根目录若躺着 `NUL` 一并删。写法见 `docs/使用手册.md` §7.1。
- **出处**：`packs/x6pro/DEVLOG.md` §7。

### 6.4 `UNPROTECTED PRIVATE KEY FILE`
- **判定**：ssh 拒绝使用 `tools/ssh/id_devvm`；用 `attrib` / `icacls` 看该私钥权限。
- **根因**：私钥文件权限太宽。
- **修法**：跑 `bootstrap.py --only ssh-key`（内部用 `icacls` 收紧，期望只有 `lbdl:(R)`）。
- **出处**：`README.md#已知问题排查`；`docs/使用手册.md` §12。

### 6.5 双击 `ssh-vm.cmd` "闪一下就没了"
- **判定**：先 `where ssh`；`no ssh in PATH` = 没装 Windows 的 OpenSSH 客户端可选功能，或在 Git Bash 里跑。
- **根因**：双击走的是**系统 PATH**（不是 Git Bash 的 PATH）；老脚本不 `pause`，报错随窗口关闭一起消失。另：`.cmd`/`.bat` 里**只能写 ASCII**——cmd.exe 按 OEM 代码页读，中文会把 `echo` 行拆坏。
- **修法**：用新版 `ssh-vm.cmd`（先 `where ssh` 预检，失败时打印退出码 + 排查顺序再停住等按键）；退出码含义见 `docs/使用手册.md` §7.1 的表。
- **出处**：`docs/使用手册.md` §7.1；`packs/x6pro/DEVLOG.md` §7。

### 6.6 adb 连不上 / `adb devices` 里冒出重复的 `emulator-XXXX`
- **判定**：`dpctl status` 先确认 VM 在跑；`dpctl sh -c "cat /tmp/adbd.log"`。莫名多出 `emulator-XXXX` 时看宿主转发端口。
- **根因**：前者多半是 guest 的 `adbd` 没起来；后者是宿主转发端口落回了 adb 的模拟器探测区间 **5554–5585**。另外这族 adbd 是 android-tools 4.2.2，**只走 USB gadget**，TCP adb 本就不可用。
- **修法**：`python scripts\dpctl.py adb`（内部自动在 guest 拉起 `adbd` 并 connect；重启后 `/data/misc/adb/adb_keys` 由 `dpctl` 重新预建）；宿主端口已用 **15037** 规避；该族改用 SSH / 串口传文件。
- **出处**：`README.md#已知问题排查`；`docs/使用手册.md` §7；`packs/x5pro/README.md` §2。

## 7. 状态盘：只读、盘满、黑屏

### 7.1 串口 `errno: 28` + `Read-only file system` + `No space left on device`
- **判定**：`dpctl sh -c "df -h /state"`；串口里 `overlayfs: failed to create directory /state/work/work (errno: 28)` 就是判据（`errno 28` = ENOSPC）。
- **根因**：overlay 的 upper 层（`/state/upper`）与盘上其他数据在同一块 ext4 上；盘满时连 workdir 都建不出来 → 整个 overlay 只能**只读挂载** → **所有 S00 钩子（凭证、触摸桥、电量、热点、`replace`）全部写不进去** → 笔的 UI 起不来（黑屏）+ guest 服务反复重启。
- **修法**：把 `[state].size_mb` 调大再 `up --fresh`；框架的 `/init` 也会在 overlay 之前自动清厂商 swap 文件（`/userdisk/swap/swap.file`，实测 257 MiB 而 `/proc/swaps` 里 `Used=0`）。**不要**去删 `/userdisk/secondary`（那是 miniapp 解压二级应用的真实路径）。
- **出处**：`packs/a7pro/README.md#两个已修复的问题`；`docs/插件模型.md` §5.5；`README.md#已知问题排查`。

### 7.2 `corefile` 堆到几万个文件把状态盘顶满
- **判定**：`dpctl sh -c "ls /userdisk/corefile | wc -l"`（正常 ≤ 500，实测曾到 27877 个 / 111 MB）；`df -h /state` 接近满。
- **根因**：guest 的 `CapFrame` / `run_input_event_monitor` 每秒写一个崩溃日志到 `/userdisk/corefile`，堆积把 512 M 盘顶满；之后 guest 侧开始 `can't create ...: No space left on device` 并进入崩溃循环，表现为**点击完全没反应**（输入子系统已死）。
- **修法**：新 initramfs 自带 `S00corelog`——开机把 corefile 裁到最新 `DICTPEN_COREFILE_KEEP`（默认 500）个，并常驻 janitor 每 `DICTPEN_COREFILE_INTERVAL`（默认 600 s）再裁一次，`DICTPEN_COREFILE=0` 可关掉。**万一已顶满**（历史积压，不是新钩子的错）：`dpctl down` → `dpctl up --rescue`（不启 pen 的 init，串口直接给 root shell）→ 删掉 `/userdisk/corefile/*` → 再正常 `dpctl up`；空间恢复后点击立刻正常（`--rescue` 下没有 SSH/adb）。
- **出处**：`README.md#已知问题排查`；`packs/s7pro/README.md` §8。

### 7.3 单个 `Capframe_*.log` 长到几个 GB
- **判定**：`df` 显示 `/userdata/applog` 占大头，单个 `Capframe_*.log` = 2,981,621,760 字节且还在涨。
- **根因**：`runCapFrame/CaptureFrame` 的启动点在 **S01systeminit**（`/usr/bin/guardian_run /usr/bin/runCapFrame`，无 `&` 结尾）——按 a6pro 语义只静默 `S50launcher*` 的形态会漏掉这台。
- **修法**：fixup 的静默 sed 按 `S*` 通配 + 匹配带不带 `&` 的两种形态；另装 `S00applog-cap` 兜底（`Capframe_*.log` 直接清、`DictPen_*.log` 留最新 10 份）。
- **出处**：`packs/s7pro/README.md` §8。

### 7.4 `/state` 是空目录（以为没持久化）
- **判定**：`dpctl sh -c "ls /state"` 空。
- **根因**：`/data`、`/misc` 本身是**软链**（分别指向 `/userdata` 与块设备）；持久化落在 `/state` 与 `/userdata`。
- **修法**：不要往软链名的目录里找；调整你的判据去看真身。
- **出处**：`README.md#已知问题排查`。

### 7.5 改动重启后就丢了
- **判定**：`dpctl status` 看 `state:` 那一行；串口日志有没有 `### state: ext4 created and mounted ###` 与 `### overlay: persistent upper ###`。出现 `state: unavailable ...` = 格式化/挂载失败（会自动回落 tmpfs，不影响开机）。
- **根因**：状态盘没生效。
- **修法**：`up --fresh` 重建本包的盘；改了 `[state].size_mb` 也必须 `up --fresh`（该设置**只在创建时生效**）。
- **出处**：`README.md#已知问题排查`；`docs/使用手册.md` §8。

### 7.6 明明有 `S00corelog` 却"没拦住"盘满
- **判定**：串口里仍有 `Read-only file system`，而钩子看着装上了。
- **根因**：**鸡生蛋**——`S00corelog` 是装到 guest 里的，而装它的那一步就失败在只读 overlay 上。所以清理必须在 `/init` 里、overlay 建 upper **之前**做，直接对 `/state` 干活。
- **修法**：用 §7.2 的 `--rescue` 先腾出空间再用。
- **出处**：`packs/a7pro/README.md#两个已修复的问题`。

## 8. 其他

### 8.1 点中卡片后约 80 ms SEGV（点空白不崩）
- **判定**：guest gdb——断点打在 `packLog` 里 `bl <operator[]@plt>` 的下一条、条件 `$r0 == 0`；命中 `_Map_base<...>::operator[]` 返回 0，紧接 `std::string::_M_assign(this=0, ...)` → SEGV。栈顶是 `YLogSpyEntity::packLog` ← `YLogSpy::spyMultiple` ← `YLogManagerModulePrivate::logSpy` ← `JSLogManagerProxy::logSpy`（埋点链路）。
- **根因**：`unordered_map<string,string>::operator[]` 是 **WEAK 模板实例**，libstdc++.so 不导出（GCC6 起改成头文件内联），全进程靠"谁先加载谁兜底"；而「全导出桩化」的 `libyocr.so` 里那份替别人兜底的弱定义也被换成了 `mov r0,#0; bx lr` → 埋点一发即崩。
- **修法**：`patches/fix-stub-cxxrt.py <原始.so> <桩.so> <输出.so>` 只把 `.text` 里属于 C++ 运行期符号（`_ZN?St*`、`_ZN?9__gnu_cxx*`、`_ZSt*`、new/delete、`__cxa_*`、`_Unwind_*`）的字节从原始库回填，其余一律不动。**判据顺序记牢**：先 `stubaudit` 列被抹掉的运行期符号，再在 guest 侧扫该机全部 ELF 的 `.dynsym` UND 表取**交集**——命中为 0 就不必回填（x6pro 实测命中 0，**结论是不用修**；x5pro 命中，回填 382/166 个符号）。
- **出处**：`packs/x5pro/README.md` §10；`packs/x6pro/DEVLOG.md` §5.6(3)。
- **取证坑**：`/proc/<pid>/mem` 用 perl `seek` 读 `0xf3xxxxxx` 会因 32 位 `off_t` 溢出**静默失败**（读出全 0，看着像"GOT 未解析"）——读高地址一律用 gdb。

### 8.2 OCR 让 miniapp 秒崩、guardian 无限重启
- **判定**：`DictPen_*.log` 里 `[OCR INFO] ydstitch_init` 之后 `CviDeviceMem::device_init(...): Assertion '0' failed.` → `Aborted`。
- **根因**：libyocr 初始化链要 **CVITEK TPU**（`/dev/ion`、`/dev/cvi-tpu0`），VM 没有。
- **修法**：`patches/libyocr.so` + `patches/libYoudaoStitch.so` = 真库的**全导出桩化版**（名字含 init/open/create/load/setup/start 类返回 -1，其余返回 0），经 `[adapt.replace]` 整体替换；**不改 `DT_NEEDED`、不动 presetpkgs 的 `.amr`**（依赖链自然解析到桩上）。**桩化必须保留构造器**：中和构造器会让应用启动即 **SIGILL**。
- **出处**：`packs/s7pro/README.md` §4；`packs/x5pro/README.md` §4。

### 8.3 桩化脚本自身的两个坑
- **判定**：桩化后 `ydstitch_init` 照跑（日志还有 `ydstitch_init time: …`），然后 `symbol lookup error`。
- **根因**：**ELF32 的 `Elf32_Sym` 是 16 字节**（ELF64 才是 24），按 24 步进会错位读出垃圾、真入口漏桩。
- **修法**：按 16 字节步进。回归时还要注意 **overlay upper 的 whiteout** 会挡住 `[adapt.replace]`（whiteout 是字符设备 0:0，会让 `[ -e ]` 永远为假）——fixup 里用 `[ -c ]` 判断后 `rm`，**不要**对 lower 层的普通文件跑 `rm -f`（会制造新 whiteout）。
- **出处**：`packs/s7pro/README.md` §4。

### 8.4 报"该平台 runtime 未实现" / 改了包却"启动结果没变"
- **判定**：前者 `python scripts\dpctl.py packs <名>` 会打印框架现有的 runtime 名字；后者是改动"看起来没生效"。
- **根因**：前者是 `[platform].runtime` 拼错或平台未支持；后者是 initrd 按哈希缓存（`packlib.ensure_initrd`），尤其**改了 `scripts/initramfs-init.sh` 必须重打 base**，否则 `up` 照旧复用旧 initrd。
- **修法**：改对 runtime 名或按 `docs/固件包开发教程.md` §7 写一个（全部失败表现见 `docs/插件模型.md` §3.3）；缓存问题跑 `python scripts\build-initramfs.py`，必要时删掉 `vm/initrd-<包名>.cpio.gz*` 再启动。
- **出处**：`README.md#已知问题排查`；`docs/固件包开发教程.md` §8.3；`packs/x6pro/DEVLOG.md` §7。

### 8.5 进桌面约一分钟后自己关机（提示低电量）
- **判定**：`dpctl sh -c "cat /sys/class/power_supply/battery/capacity"` 应是 **80**；不是 80（或报错）说明没伪造成功。
- **根因**：`/sys/class/power_supply` 是空的，电量被读成 0%，`S00battery` 钩子没生效。
- **修法**：包内开 `[adapt].battery`（电量栈不是这么读的机型别开）；并确认 initramfs 是最新构建。
- **出处**：`README.md#已知问题排查`；`docs/使用手册.md` §12。

### 8.6 `Attempted to kill init!` 重启循环 / 模块签名被拒（`Key was rejected by service`）
- **判定**：
  - 串口里 `Kernel panic - not syncing: Attempted to kill init! exitcode=0x00000200` 反复出现
    （一次开机能刷出十几轮），且 panic 前最后一行是
    `/init: /patches/hooks/<某钩子>.sh: line N: syntax error: unexpected word (expecting "do")`
    → **钩子脚本带 CRLF**。包的钩子是 `source` 进 PID 1 的，一句语法错就让 init 退出、内核 panic。
  - 改过的 `.ko` 加载时报 `Key was rejected by service` → 模块签名被拒。
- **根因（CRLF 那条）**：这个项目会把脚本**烘进 Linux guest 的 initramfs** 执行；
  Windows 上 `core.autocrlf=true` 时 clone / `git checkout` / `git rebase` 会把工作区脚本
  转成 CRLF，下一次 `up` 触发 initrd 重建就把 CRLF 烘进去 —— 于是机器再也起不来。
  注意：**仓库里的内容本身是正确的 LF**，坏的是工作区副本。
- **修法**：
  - 仓库已加 `.gitattributes`（`* text=auto eol=lf`，`.cmd/.bat` 例外），根治这类转换；
  - 已有的脏工作区：把相关文件转回 LF，然后 **必须**
    `python scripts\build-initramfs.py` 重打 base（否则每包 initrd 仍按旧 base 的指纹复用）；
  - 改任何 initramfs 脚本后，先 `bash -n scripts/initramfs-init.sh` 再重打。
  - 模块签名：剥离尾部签名（`Module signature appended` 及其前面的 12 字节结构）。
- **出处**：2026-10-17 实测（`packs/x6pro/patches/prepare.sh` 被转 CRLF → x6pro 启动 panic 循环，
  修 LF + 重打 base 后恢复正常：串口 0 panic、截屏 221 KB = 桌面）。

### 8.7 PySide6 装不上 / vmgui 起不来

### 8.8 应用点开全黑，可注册项和文件**都在盘上**

### 8.9 实体键全不工作 / `m_homeModule.init failed res== -14`
- **判定**：`/userdata/applog/vm-miniapp.log` 里 `[YButtonEventAdapter] [init]` 连续报

- **修法（通用）**：在 **app 启动前**把 `/proc/device-tree/model` bind mount 成该机真机串

- **时序（踩过两次）**：

### 8.10 没声音：先查宿主默认端点，再看客机的工具链
- **判定**：客机 `/proc/asound/cards` 有 `card0 QEMU USB Audio`，`aplay -D plughw:0,0 x.wav`
  rc=0；但听不到。这时先别怀疑 VM——查 Windows 默认播放端点的音量/静音。实测这台
  在 2026-10-20 是 `扬声器 (Senary Audio)` **0% + 静音**，2026-10-21 又变成 **9% + 静音**，
  所有型号一起哑。控制台声音页现在有常驻提示；改完宿主端点再按「测一下」。
- **修法**：解除宿主默认端点静音并把音量调起来（本机调到 25%）。客机侧 7 台都有 USB 声卡；
  x6/s6/s7/x5/x7 带 `aplay/amixer`，a6/a7 只有 tinyalsa：用 `tinyplay -D 0 -d 0` 播
  **48 kHz 立体声**，44.1 kHz 单声道会 `cannot set hw params: Invalid argument`。
- **已证**：播放时客机 `pcm0p` 是 `RUNNING`、48 kHz；用 `DICTPEN_AUDIODEV=wav` 起机，
  QEMU 落盘的 `vm/audio-capture.wav` 里有真实 440 Hz（峰值 11295）——客机→QEMU 这段没问题，
  剩下就是宿主端点。`wav` 后端会拖慢客机，只用于诊断；日常用默认 dsound，必要时
  `DICTPEN_AUDIODEV=sdl` 换 SDL。
- **声音页**：选中另一个操作会杀掉上一条命令（不再等“上一条命令尚未返回”）。快速启动的
  快照不含音频，页面会直接写“要声音请用普通「启动」冷启动”。
- **音量键**：只有 x6pro 的 key config 有音量键（115/114）；其余型号的节只有
  home/head/power，工具条上的音量键对它们没有意义。
- **出处**：台账 Q91；探针 `vm/_qwen_model_probe.sh`。

### 8.11 启动慢：先别加配置，这是 TCG 模拟；首页快照约 6 s
- **实测（x6pro）**：`dpctl up` 本身 4 s，SSH 33 s，首页 55–62 s。试了 `-cpu max/a55/a72`、
  1/2/4 vCPU、1/2 G 内存、`tb-size=1024`：SSH 都约 33 s，首页 62–77 s，**没有实质收益**。
  实机配置更低却更快，是因为它是原生 ARM；这里是 TCG（x86 上无 ARM 硬件加速），瓶颈在模拟。
- **快照**：先关机，`dpctl fast save --pack <包>` 会把**普通状态盘**复制成独立的
  `vm/fast-<包>.qcow2`，无音频冷启动到首页后 `savevm ready`；之后 `dpctl up --fast`
  （或控制台「快速启动」）用 `-loadvm ready` 恢复，实测 **SSH 5.6 s、画面 6.2 s**。
  `dpctl fast status` 查快照时间/机器参数。
- **声音**：usb-audio 在 QEMU 里不可迁移，所以快照必须 `--no-audio`；HDA
  （`intel-hda+hda-duplex`）能过 savevm，但客机 `no soundcards`（codec 没 probe），
  因此快照就是无声音的。要声音用普通「启动」冷启动；音量/声音模块只在冷启动里。
- **记住三条**：快照盘与普通状态盘独立（普通启动的改动不进快照）；快照运行期的改动
  下次快速启动会丢弃；机器参数（mem/smp）与快照不一致时 `up --fast` 拒绝。
- **入口**：`dpctl fast save/status`、`dpctl up --fast`；控制台工具条「快速启动」「保存快照」。
  保存快照约 1.5–2 分钟，控制台会先要求关机并确认覆盖。
- **出处**：台账 Q93；测量脚本 `vm/_bootbench.py`；截图 `vm/_fast_resume.png`。

### 8.12 蓝牙连不到外部设备：那是客机的虚拟控制器，不是电脑蓝牙
- **口径**：控制台「蓝牙」页的开关/扫描都在**客机 `hci0`** 上；链路是
  `hci_uart`（`/dev/ttyAMA1`）→ 宿主 `scripts/bt-hci-emu.py`。它没有真实射频，
  也不碰 Windows 的蓝牙适配器；所以既不会连电脑的蓝牙，也看不到电脑周围/已配对的设备。
- **能做什么**：上电（`btmgmt power on` + `le on`）、有界扫描
  （`btmgmt --timeout 8 find`）。扫描会触发模拟器里的假设备
  `11:22:33:44:55:66`（`vm/bt.log` 可见），但 `btmgmt` 的文本输出不列出它，
  连接/配对语义也还没实现；控制台「连接」已禁灰并写明原因。
- **不能做什么**：连真实耳机/音箱、传文件、用电脑的蓝牙。宿主这台有 Intel 蓝牙，
  但 VM 没用它；内置适配器也不能直通。
- **要连真实设备**：给 QEMU 加 `usb-host`，把一只独立的 USB 蓝牙 dongle 交给客机，
  并把 `btusb` 模块补进 initrd（内核树里有 `btusb.ko`）。这条要实机 dongle 才能验；
  Linux 宿主也可以走 vhci，Windows 宿主没有等价的内置通道。
- **别用**：`bluetoothctl --timeout 8 scan on`——`bluetoothd` 没起来时会挂住 D-Bus
  （实测 SSH 60 s 超时）；控制台已改用 `btmgmt`。

### 8.13 设置里的存储是 -1GB / 扩容后不跟随
- **-1GB**：x6pro 等机型停用了真机的 `S21mountall`，guest 里没有 `/dev/block/by-name`；
  设置页的 `getStorageInfo` 打开它失败就回 `-1`。strace 实测
  `openat("/dev/block/by-name", O_DIRECTORY) = -1 ENOENT`；补上
  `userdata/userdisk -> /dev/vdb`、`system_a/b -> /dev/vda` 后，日志从
  `getStorageInfo fail` 变成 success，页面显示 4GB。x6pro 已固化到 `S50vm-ui`。
- **为什么是 4GB 且不跟随**：厂商 `getStorageInfo` 返回固定 JSON
  `{"totalSpace":4,"firmware":4036,"resource":60,"user":0,"available":0}`。
  页面用 `totalSpace`（GB）、`user`（已用 MB）、`available`（可用 MB）；后两项都是 0，
  所以永远是满的 4GB。状态盘扩容不会改变这组值。
- **x6pro 已修（Q99）**：用 preload shim 覆盖 `libyddal_adapter.so` 的同名
  `getStorageInfo`，返回 `statvfs("/userdata")` 的 total/used/free；`prepare.sh` 把
  shim 放 `/usr/lib`、把 `/usr/bin/miniapp` 换成 `LD_PRELOAD` wrapper。
  实测 2G 盘显示 0.4GB/2GB，扩到 3G 后显示 0.4GB/3GB（跟随）。
- **s7pro 已修（Q104）**：注意它的 app/adapter 是 **ELF32 armhf**（glibc 2.33），
  x6pro 的 AArch64 shim 不会被加载；要用 `zig cc -target arm-linux-gnueabihf` 编同符号
  shim（r0=sret、r1=this、24B string）。同一份 shim 还把
  `YAsyncLocalTranslatorPrivate::loadNmtPatchEv` 做成 no-op——`/userdisk/uresource/localdict`
  缺失会抛 `MiniNmtException` 让 app abort（本地翻译因此不可用）。
  装法也不同：`[adapt.replace]` 的 `S00replace` 只覆盖**已存在**的目标，新增的
  `/usr/lib` 文件要在 `fixup.sh` 里直接拷进 `$TARGET`；`runDictPen.sh` 首 app 前换 wrapper。
  实测 6G 盘「空间清理」与「关于→存储容量」都显示 1.8GB/6GB。
- **s6pro 已修（Q105）**：app 是 **ELF32 armhf + glibc 2.23**（比 s7 更老），shim 要在
  s6 的 libc 上重编；并且**必须带 NMT no-op**——一旦覆盖存储符号，`loadNmtPatch` 在
  `localdict` 缺失时会抛 `MiniNmtException` 让 app abort（表现为 app 每 10 s 重启一次、
  首页停在最后一帧）。shim 放 `/usr/lib/vmstorage/` 子目录，不要放 `/usr/lib` 顶层
  （这台 app 的加载器会把顶层 .so 当缺失库候选打开）。实测 8G 盘两条入口都显示 0.5GB/8GB。
- **s6pro 的设置版本要钉 2.1.1**：2.1.6 的 SettingsManager 只 `require('settings')`，
  而本机只有 `services/settings.js.bin`，存储/关于页会 `could not load module` 全黑。
  联网后 app 会自动升级到 2.1.6（log 里 `oldVersion=2.1.1 newVersion=2.1.6`），
  包的 `fixup.sh` 把 `hardware-iot.youdao.com` 指到 127.0.0.1。已有 2.1.6 状态盘
  手动降一次：`miniapp_cli install /etc/miniapp/resources/presetpkgs/8080272425914438.amr`。
- **x5pro 已修（Q106）**：与 s6pro 同为 armhf + glibc 2.23，直接复用同款 shim
  （含 NMT no-op），实测 1G 盘两条入口都显示 0.4GB/1GB。x5 的设置列表同样是
  从卡片内部上拖才滚得动；它的 `S50vm-keys` 会停掉守护链直接起 miniapp，wrapper 必须
  在首次 runDictPen 时就装好（本包已这样做）。
- **a6pro 已修（Q107）**：app 是 **uClibc**（`ld-uClibc.so.0`），glibc shim 不能加载；
  shim 做成 libc-free（`statfs` raw syscall + libstdc++ `operator new`）。**不能用 malloc**
  分配返回字符串——a6 的 app 重载了 new/delete，用 malloc 会被它的 delete 释放时崩。
  NMT 是库内绑定，preload 的 no-op 拦不住；包内替换 `libyddal_base_nmt.so`，把
  `loadNmtPatch` 首指令改成 `bx lr`。实测 1G 盘两条入口 0.3GB/1GB。
- **其他机型**：先看 `prepare.sh` 是否停用 `S21mountall`、fstab 分区名（缺 by-name
  会 -1），再确认 app 是 AArch64 还是 armhf、glibc 版本；若也要跟随，用同符号、
  同位数、对应该 glibc 的 shim。不要照抄 x6pro 的路径。
