# 固件能力盘点（以 a6pro 为样机）

> 目的：从“VM 能开机、能显示”转向“miniapp 以为自己在一台什么设备上”。
> 本文只做固件与运行时分析，不包含功能改动。样机 a6pro（Pear_RV1106，YoudaoOS 4.7.4）。
> 取证日期：2026-10-21；框架：Debian 6.1 内核 + 厂商 rootfs overlay。

## 0. 结论摘要

当前 VM 已经解决了**引导、显示、触摸、网络、实体键、设置页存储展示**，但 miniapp 依赖的
**设备契约**仍有多处缺口：

1. **存储/下载**：`hal-storage` 的 `get_storage_info` 失败；`/dev/block/by-name` 指向的
   `mmcblk0p*` 在 VM 里不存在，`/uresource` 为空目录、`/userdisk/uresource` 不存在。
   `YResourceManager` 的 `isDiskSpaceAvaliable`/`Out of space` 路径因此不可用。设置页的
   `getStorageInfo` shim 只修了“显示”，没有修下载器看到的存储。
2. **音频**：厂商音频 HAL 走 tinyalsa，期望 `card1`（`/sys/class/sound/card1`）和 codec mixer
   控件（`DAC LINEOUT Volume`/`Playback Volume`）；VM 只有 QEMU USB Audio `card0`。
   `hal-audio-volume` 实测 `is_okay=0`，音量设置没有落到应用实际播放的声卡。
3. **亮度**：厂商 HAL 期望 `/sys/class/backlight/backlight/*` 与
   `/sys/devices/platform/backlight/...`；VM 的 `/sys/class/backlight` 为空。`hal-screen get`
   读到的 30 来自 `/userdata/cfg/sys_config.conf`，不是硬件，set 无法映射到显示端。
4. **设备身份/厂商节点**：`vendor_storage` 打开失败，`/dev/vendor_storage` 不存在；SN/SKU/激活
   依赖的厂商存储没有真实实现，当前靠 S00/S99 license 和命令行参数绕过。
5. **SSH 的 `C:`**：当前客机 `/` 没有 `C:`，`/proc/mounts` 没有 9p/virtiofs，宿主 2222 的
   监听者是 QEMU。用户看到 `C:\Users\<用户名>` 的那次会话**很可能不在客机**；需要用原始命令复现
   后再定性，不能直接称为客机逃逸。
6. **原生 miniapp 结构已经测绘完**（见 §8）：`miniapp.real → falcon_entry → libfalcon` 是薄壳，
   能力都在“JS 包（`.js.bin`）+ 每应用两个原生库（`libjsapi_*`/`libbusiness_*`）+ YDAL + YHAL”
   这条链上；20 个二级应用的清单、版本、机型代号开关与文件校验表都拿到了。三个症状分别落在这
   条链的 HAL 层（音量、亮度）和原生 `statfs64` 层（下载空间），后续任何改动都应该按这张分层表
   选层，而不是继续在 `miniapp` 外面套 wrapper。

7. **机型之间差异比预想大**（§9）：x6pro 用 weston+seatd、glibc aarch64、应用装在
   `/userdisk/miniapp/.../a/`，音量 HAL 查 `/usr/configs/youdao_hal_audio_config.json` 的板级表
   （命中 `RK3562_Melon_V0`，`speaker_card_id=0`、`numid=3`），`hal-audio -s 40` 之后
   `amixer -c 0 cget numid=3` 从 240 变 153，音量确实写进了 ALSA 控件；s7pro 查的是
   `speaker_card_id=1`/`numid=4`，同一条命令回 `is_okay=-22`（`-EINVAL`）且 mixer 不动；
   a6pro 是 falcon 直连 DRM、uClibc、tinyalsa 硬编码 `card1`，应用日志 `is_okay:0`。
   注意 get 路径上的 `is_okay` 与 `check [true]` 只是 sys_config 的回显，不能当证据。
   七台全部跑完后（§9）：`/sys/class/backlight` 全空、`/userdisk/uresource` 全无；
   音量链路只有 x6pro 通，其余分别断在“表要 card1～card4”（s6pro/x5pro/s7pro）、
   “板级键解析不出”（x7，`init error:-1`）、“tinyalsa 硬编码 card1”（a6pro/a7pro，
   其中 a7pro 连 `hal-audio` 和板级表都没有）。

8. **离线核证已经跑通**（§11）：镜像本来就挂在客机 `/dev/vda`，`mount -t erofs -o ro`
   就能看到固件原值。这一趟推翻了两条今天的表述——固件里只有一个 `/usr/bin/miniapp`
   （`.real` 是我们的改名），以及厂商 `cfg.json` 本来是 `16 bpp + direction 270`、
   是我们改成 `32 bpp + direction 0` 的，R/B 颠倒因此要重判根因层级。
   另有一条正向线索：NMT 缺的 `localdict`/`localsound` 在固件里是指向
   `/userdisk/uresource/*` 的符号链接，缺的是挂载点，不是文件。

一句话：**现在的 VM 是“行为像”的适配层，还不是一台对 miniapp 完整的虚拟词典笔。**

## 1. 运行栈：Debian 只是内核

```
QEMU aarch64
  └─ Debian 6.1.176-1 arm64 内核（框架提供）
       └─ 厂商 rootfs（只读 erofs/ext4）作为 lower
            + /state/upper、/state/work 组成 overlay /
       └─ 厂商 /init、/etc/init.d/rcS 与 S01/S20/... 启动厂商服务
       └─ 框架 S00/S99 钩子补充 VM 设备与文件
```

- 用户态不是 Debian：`/usr/bin/miniapp`、`hal-*` 都是 **ELF32 ARM uClibc**，解释器
  `/lib/ld-uClibc.so.0`；不是 Debian glibc 用户态。
- 内核是 aarch64 + COMPAT，因此 ARM32 厂商程序能跑；但“能跑”不等于“设备接口对得上”。
- 框架 overlay 的 upper 在 `/state`，厂商 rootfs 是 lower；`/userdata`、`/userdisk` 都是
  `/dev/vdb` 的挂载点（a6 状态盘 1 GiB）。

## 3. 设备契约与缺口

### 3.1 存储（P0，直接对应“下载音频提示空间不足”）

**固件期望**（来自 `libydhal_devices.so` 与 `ResourceManager` 字符串/行为）：

- `/dev/block/by-name` 下的 `userdata`、`userdisk`、`uresource` 等分区；
- `/proc/partitions` 中的 `mmcblk0`；
- `/sys/block/<dev>/size`；
- `/userdisk`、`/userdisk/uresource`；
- `/uresource/resource`，以及 `mount -o remount,rw /uresource`；
- `YDictManager::isDiskSpaceAvaliable`（应用包内的 `libbusiness_settings.so`）与
  `Out of space`/`Not enough space`/`Statfs error`；下载本身走
  `YDALBASEAPI::YHttpManager::asyncDownload`（cpr/curl）。上一版写的
  `YDownloadManager::isDiskSpaceAvaliable` 与 `Out of disk space` 在本轮拿到的 core YDAL 与应用库
  里都找不到符号，属于误记，已按实测更正；§3.1 的“待抓 statfs 目标”结论不变。

**VM 实际**：

```
# /proc/partitions
 254 0 1310720 vda
 254 16 1048576 vdb

# /dev/block/by-name/userdata -> /dev/mmcblk0p10
# /dev/block/by-name/userdisk -> /dev/mmcblk0p11
# 但 /dev/mmcblk0p* 不存在
```

`hal-storage` 实测：

```
vendor_storage open fail
cat: can't open '/sys/block/mmcblk0/size': No such file or directory
p_dir == NULL! No such file or directory.
start storage test
```

`/uresource` 是空目录；`/userdisk/uresource` 不存在。`ResourceManager` 需要的
`/uresource/resource` 也不存在。

**结论**：设置页的 `getStorageInfo` shim 只覆盖了 `libyddal_adapter_core` 的展示函数，
没有覆盖 `hal-storage` / `YResourceManager` 的下载空间判断。高置信度解释用户看到的
“磁盘空间不足”；仍需在点击下载时抓一次 `openat/statfs` 以确认具体分支。

### 3.2 音频（P0，直接对应“音量不生效/无声音”）

**固件期望**（`libydhal_audio.so.0` 字符串）：

- tinyalsa API：`pcm_open`、`pcm_writei`、`mixer_*`；
- `/sys/class/sound/card1`；
- mixer 控件 `DAC LINEOUT Volume`、`Playback Volume`、`digital volume ctl`；
- `/data/cfg/sys_config.conf` 中的 `spk_volume`/`ahs_volume`；
- 播放格式固定 48 kHz、双声道、S16_LE。

**VM 实际**：

- `/proc/asound/cards` 只有 `card0: QEMU USB Audio`；没有 `card1`；
- `hal-audio-volume` 实测输出 `TEST type=0, volume=80, is_okay=0`，即设置失败；
- `hal-audio-volume`/`libydhal_audio` 的 mixer 控件在 USB 声卡上也不存在。

**结论**：宿主 dsound 只保证“QEMU 有音频出口”，不等于应用走厂商 codec 的音量路径。
需要先确认 app 播放是否 fallback 到 card0；如果坚持走 card1，就必须造一个虚拟 codec
（或把 HAL 的 card/mixer 路径映射到 USB 声卡）。§8.4 的运行时日志确认了失败点在 HAL 回读；
§9.1 补上判据：真正能证明写入的是 `amixer cget` 的数值变化，`is_okay` 只是 sys_config 回显。

### 3.3 亮度（P1）

**固件期望**（`libydhal_devices.so`/`hal-screen` 字符串）：

```
/sys/class/backlight/backlight/bl_power
/sys/devices/platform/backlight/backlight/backlight/brightness
/sys/class/graphics/fb0/blank
/sys/class/drm/card0-DPI-1/dpms
```

**VM 实际**：

- `/sys/class/backlight` 为空；
- `/sys/devices/platform/backlight` 不存在；
- `hal-screen get` 返回 `get_brightness: 30`，来自 `/userdata/cfg/sys_config.conf`
  的 `brightness=30`，不是硬件读数；
- `set` 没有可写的 backlight 节点，`Failed to map2brightness` 字符串对应的映射链断开。

**结论**：需要虚拟 backlight 设备或 HAL 映射；当前应用亮度只改配置，不改画面。
运行时日志（`getTpUpdateStatus sec failed ret:-1`）见 §8.4。

### 3.4 设备身份 / vendor_storage（P1）

- `vendor_storage` 二进制打开 `/dev/vendor_storage` 失败；
  `get_sku`/`get_sn`/`get_cmei` 等依赖它。
- VM 当前用 `DICTPEN_SN/UUID/MODEL/SKU` 参数和 S00sysinfo/S00license 绕过，属于**适配层**，
  不是设备契约。
- 影响：激活、商店、设备信息、部分业务分支；x7 的 dev license 验签问题就是这类后果。

### 3.5 LED（P2）

- `hal-led` 读 `/usr/configs/hal_led_config.json`，本机配置 GPIO 122（IR）和 118（白灯）。
- VM 有 `gpiochip0`，但没有这些 line；实测 `module.init failed!`。
- LED 不影响主 UI，但属于“设备在不在”的观测点。

### 3.6 相机 / OCR（P2，已知）

- `hal-camera` 依赖 sharering、CVITEK/RKNN 共享内存；VM 中 OCR 栈已桩化。
- `libyocr`/`libYoudaoStitch` 桩化只保证“不崩”，不代表相机/OCR 可用。

### 3.7 按键 / 电池 / 网络（部分已适配）

- 按键：真机是 gpio-keys/adc-keys；VM 用 uinput + `vm-keys`，Home 只解决“事件可达”，
  不是完整的按键 HAL。
- 电池：S00battery 造 `/sys/class/power_supply`，`hal-battery` 能读 capacity，属于可接受的
  虚拟设备。
- 网络：虚拟 AP + wlan0/eth0 双栈；已能保持 COMPLETED，但这是框架网络，不是厂商
  bes2600 芯片契约。

## 4. 现有适配 vs 真实设备契约

| 能力 | 当前实现 | 性质 |
|---|---|---|
| 引导/显示 | falcon + bochs-display + overlay | 框架适配，基本可用 |
| 触摸 | uinput touchbridge/鼠标桥 | 输入契约替代 |
| 实体键 | uinput + vm-keys | 输入契约替代，仅 Home/部分机型 |
| 电池 | fake power_supply | 可接受的虚拟设备 |
| 网络 | hwsim AP + wpa 配置 | 框架网络，不是 bes2600 |
| OCR | libyocr/libYoudaoStitch 桩 | 功能不可用，只防崩 |
| 设置存储 | adapter `getStorageInfo` shim | **展示层**，不覆盖 HAL/下载 |
| NMT | 跳过 `loadNmtPatch` | 功能不可用 |
| 激活 | dev license + x7 verifyLicense bypass | 适配层，不是服务器激活 |
| 音频 | QEMU USB Audio + 宿主 dsound | 播放出口，不是厂商 codec |
| 亮度 | 无 backlight 设备，仅配置值 | 应用侧无效 |
| 存储/下载 | 无真实 uresource/by-name | **缺口** |

## 5. SSH 的 `C:` 核查

当前客机（a6pro）取证：

- `/` 列表没有 `C:`；`/C:`、`/C:/` 不存在；
- `/proc/mounts` 没有 9p、virtiofs 或宿主共享；
- 宿主 `127.0.0.1:2222` 的监听者是 QEMU（pid 与 `dpctl status` 一致），不是宿主的 sshd。

因此，用户看到 `C:\Users\<用户名>` 的那次会话**很可能不是客机**（宿主/WSL/Git Bash 或另一个
本地 shell），而不是客机逃逸。要定性必须拿到原始命令、提示符和工作目录。若确认是宿主
shell，问题是入口混淆/宿主暴露，不是 guest→host 逃逸；若在客机里复现出宿主目录，则说明
存在未记录的共享挂载，属于真实逃逸面，需立即处理。

## 6. 缺口优先级（仅分析结论）

1. **P0 存储/下载**：`by-name` 目标设备、`uresource` 分区/目录、`hal-storage` 返回；
   先抓一次下载的 `statfs/openat` 确认分支。
2. **P0 音频**：确认 app 播放走的 card/device 与 mixer 控件；决定“虚拟 codec”还是
   “HAL 映射到 USB 声卡”；`hal-audio-volume is_okay=0` 是硬证据。
3. **P1 亮度**：虚拟 backlight sysfs，或 HAL 写节点映射到宿主/显示端。
4. **P1 vendor_storage/身份**：SN/SKU/激活依赖，当前是参数绕过。
6. **P2 LED/相机/传感器**：按应用是否实际使用排序。

## 7. 下一步（分析阶段，不落地功能）

1. ~~以音量 ±/亮度 ± 为触发抓 HAL 落到哪一层~~：已用 `/userdata/applog/YD_PEN_APP.log` 与
   `libydhal_*` 字符串定到具体缺口（§8.4），需要补的是“点击下载”那一次的 `statfs64` 目标目录；
   客机没有 `strace`，可选方案是 preload 一个记录版 `statfs64`，或在真机复现。
2. 逐台最小盘点：七台已全部完成（§9）。后续只在固件版本变化时重跑
   `vm/_contract_probe.sh`（`dpctl put` 到 `//tmp/probe.sh` 再 `sh` 执行），
   音量这条链的判据固定为 `amixer cget` 的数值变化（§9.1）。
3. 逐机型确认 HAL 的 card 编号语义：a6 的 `card1` 期望来自真机 codec 布局，VM 只有 USB
   声卡 `card0`；需要一台能发声的真机或厂商文档来确认 `type → (card, device)` 映射。
4. `cert` 校验范围：替换包内 `.js.bin` 是否被拒，决定我们能否用“改包”的方式补能力。
5. 只在契约表定稿后再改代码；每次改动都带 guest 侧证据与回归测试。

## 8. 原生 miniapp 架构（a6pro 实测）

### 8.1 启动链

```
/usr/bin/miniapp            （镜像本体 5492 B，ELF32 ARM uClibc；首靴被我们的 fixup 改名成
                             /usr/bin/miniapp.real，原位放 232 B 的 LD_PRELOAD wrapper）
  └─ /usr/bin/miniapp.real  （同一个文件，只是改名后的厂商 launcher，stripped）
       DT_NEEDED: libfalcon libquickjs libJQuickBase libjsapi_proxy libydhal_devices
                  libdrm libts libcurl libcpr libz libexpat libpng16 libjpeg libqrencode
       main → falcon_entry（/usr/lib/libfalcon.so，7 882 716 B）
```

`miniapp.real` 这个名字只存在于运行态；固件镜像里它是 `/usr/bin/miniapp`（见 §11.2）。

`libfalcon.so` 读入的运行时配置与资源：

### 8.4 三条症状在架构里的位置

音量（日志原文，pid 1726，10-21 16:49:33）：

```
[YVolumeAdapter] [volumeInit] m_volume_module:0x2b515f0 m_audioHandle:0x2b51818
[YVolumeAdapter] [getVolume] YVolumeAdapterPrivate::get_volume res:0
[YVolumeAdapter] [operator()] getVolumeCallBack--->80  is_okay:0
```

`80` 来自 `/data/cfg/sys_config.conf` 的 `spk_volume=80`（同文件还有 `ahs_volume`、
`dhs_volume`、`bt_volume`），`is_okay:0` 说明 HAL 回读失败。HAL 侧要求 `card1`
（`/sys/class/sound/card1`）、mixer 名 `DAC LINEOUT Volume`/`Playback Volume`，格式固定
2ch/48 kHz/S16_LE，还会 `dlopen` `libawinic.so` 与 `librkaudio_effect_eqdrc.so`。
VM 只有 `card0`，mixer 控件名为 `Audio Output Volume Control Playback Volume`
（min −32767/max 2048）。音量滑杆因此只改配置值，不改实际输出。

亮度（pid 1726 与 2059 都有）：

```
[YBrightnessAdapterPrivate] [getTpUpdateStatus] getTpUpdateStatus sec failed--->0ret:-1
```

对应 `/sys/module/cst8xx_ts/parameters/tp_update_info` 不存在；`/sys/class/backlight` 与
`/sys/devices/platform/backlight` 也都是空的，所以 `setBrightness` 没有可写节点。

下载提示空间不足：代码里有两道门，都不经过我们做过的显示层 shim。

| 门 | 位置 | 判据 |
|---|---|---|
| 原生 | `libbusiness_settings.so` 的 `YDictManager::downloadDict → isDiskSpaceAvaliable(dir,size)` | 直接 `statfs64`，日志串 `Statfs error:`、`Out of space:`、`Not enough space` |
| JS | `JSSettingsProxy::getAppDataStorageInfo`、`YSystemInfoModule::getAvailableSpace` | `libyddal_adapter_core.so` 里的另一个方法，与 `getStorageInfo` 并列 |

`statfs64` 与 `getAvailableSpace` 都是真实文件系统读数。a6pro 状态盘 1 GiB，
`df -k /userdisk` 可用 744 460 KB，真机是 32 GB 量级，因此大资源包判“不足”属于容量结果。
资源根目录另有缺口：`libyddal_common_resourcemanager.so` 使用相对路径 `/localdict/`、
`/localsound/`，`libydhal_devices.so` 检查 `/userdisk/uresource`，客机当前没有
`/userdisk/uresource`（`/userdisk` 下只有 `corefile database miniapp music record secondary`）。

### 9.1 音量：判据与失败层级

`hal-audio` 的 `TEST … is_okay=N` 与 `check [true]!` 在 get 路径上只是 sys_config 的回显
（`Volume get value` 三台都是 `0`），所以它不能当作“落到设备”的证据。真正的判据是
`amixer -c 0 cget numid=3` 的数值有没有跟着变（实测 `hal-audio -s 40`，之后设回 80）：

| 机型 | `hal-audio -s 40` | card0 mixer numid=3 | 失败层级 |
|---|---|---|---|
| x6pro | `is_okay=40` | `240 → 153`（设回 80 后 `225`） | 无：音量确实写进 ALSA 控件 |
| s6pro | `is_okay=-22`（`-EINVAL`） | 保持 `240` | 声卡：表要 `card1/numid=7`，VM 只有 card0 |
| x5pro | `is_okay=-22` | 保持 `240` | 声卡：同 s6pro（`numid=7`） |
| s7pro | `is_okay=-22` | 保持 `240` | 声卡：表要 `card1/numid=4` |
| x7 | 没走到 set：`init error:-1` | 保持 `240` | 更早：板级键解析不出（`digital_headset_verify_path` = `(null)`） |
| a6pro | 客机无该工具；应用日志 `is_okay:0` | — | tinyalsa 版硬编码 `card1` 与 mixer 名 |
| a7pro | 客机没有 `hal-audio` 与板级表 | — | 同 a6 族，连探针工具都缺 |

x7 的应用侧同样报 `[YVolumeAdapter] [init] init error: -1` 与 `get_volume res:0`，
音量模块在应用启动阶段就没起来。

推论：x6pro 的“没声音”首要嫌疑在宿主端点（静音/音量条），应用侧的音量链路本身是通的；
其余机型断在“VM 只有一块声卡”，x7 还多一层“板级键解析依赖 SKU，而 `sku=` 为空”。
七台的 `sys_config.conf` 都记 `spk_volume=80`（s7pro 另有 `raise_pen_scan_en=1`）。

s7pro 解析到的那一栏（`speaker_card_id=1`、`speaker_vol_ctl_numid=4`、`digital_hs_card_id=2`、
`mic_subdevice_id=0`）的板级键名尚未回查，只记录了取值。

### 9.2 板级键就是机型对照表

x6pro 运行时命中的是 **`RK3562_Melon_V0`**（逐项对齐：`mic_subdevice_id=0`、
`digital_hs_card_id=2`、`digital_headset_verify_path=/sys/class/sound/card2`、
`analog_type_c_hs_vol_ctl_numid=51`、`speaker_vol_ctl_numid=3`）。
`youdao_hal_audio_config.json` 里的机型代号（`Apollo_V0/Apollo_Pro_V0`、
`RK3562_Melon_V0/RK3562_Olive_V0/RK3562_Orange_V0/RK3562_Y02_V0`、`CV1826_Melon_V0`、
`Cherry_Cvitek_1826_V0/V1_5G`、`Cherry_V0/Cherry-3566_V0`、`Plum_V0`、`PineApple_V0`、
`Almond_V0`、`Hermes_V0/V1`、`Exam_V0`、`Kiwi-3326/3566`、`Mango_V0/V1`）是厂商自己的命名，
可以拿来核对每个 pack 对应哪一栏。

板级表的版本与键数各机不同：x5pro 与 s6pro 是 16 键的 2023 版（`CV1826_Melon_V0`、
`Cherry_Cvitek_1826_V0/V1_5G` 三行取值完全相同，只有 `speaker_card_id=1`/`numid=7`，
所以拿取值无法反推键名，要靠 SKU 字符串）；s7pro/x6pro 是 30 634 B 的版本；x7 是 27 949 B、
28 键，含 `RK3562_Orange_V0`（`speaker_card_id=0`、`numid=49`、`card1` 数字耳机）。
x7 的应用上报 `client=orange model=YDPX7-1 appVersion=4.8.7`，理论上对得上
`RK3562_Orange_V0`，但运行时一个键都没解析出来，说明 x7 的 HAL 用 SKU 而不是 `client` 选行。

应用侧上报的形状（x6pro 实测）：
`client=melon model=YDPX6-2 deviceSku=OVERHEAD_X62_SKU_CHN_PRO screen=960x266
mid=Linux6.1.0-50-arm64 deviceSn=vendor_storage`，`deviceSn`/`imei` 仍是占位串
`vendor_storage`，说明 `get_sku` 失败后这些字段没被替换（七台的 `sku=` 都是空值）。

### 9.3 共同的缺口

1. 背光：七台的 `/sys/class/backlight` **全空**，`hal-screen get` 只回 sys_config
   （a6pro/a7pro/x6pro/x7 = 30，x5pro/s6pro/s7pro = 60）；`set` 没有可写节点。
2. `uresource`：七台都没有 `/userdisk/uresource`；x5pro 连 `/uresource` 都没有。
   资源根目录（`localdict`/`localsound`）无处落地。
3. 声卡数量：六台的表/tinyalsa 都指向不存在的 `card1`～`card4`（只有 x6pro 指 `card0`），
   所以“给 VM 补第二块声卡”是多机型共同前提，而且各机要的 card 编号不同。
4. 崩溃残留：a6pro 是 86 MB 的 miniapp/UbusCenter core；s7pro `/userdisk/corefile` 39 个
   （多为 `core-devmem-*`）加 14 份 `DictPen_*.log`；x7 有 7 个 core；x6pro/s6pro 各 1 个。

尚未定位的点：x7 的显示是 weston 还是 falcon（未采集）；x7 板级键为什么解析不出
（怀疑依赖 `vendor_storage` 里的 SKU）；`.amr` 与包内 `cert` 的校验时机；
`libyocr`/相机族在七台上的可用度差异。

## 11. 镜像离线核证（直读 erofs，不看 overlay）

### 11.1 方法

不需要 WSL，也不需要新工具：QEMU 本来就把只读 rootfs 挂成客机里的 `/dev/vda`，
所以镜像原值可以直接读回来，绕开 `/state` 上层。

```sh
mkdir -p /mnt/img
mount -t erofs -o ro /dev/vda /mnt/img      # a6pro：a6-2-pro-ro-rootfs.img，1.28 GiB / 内容 580 MB
```

客机内核就是挂载这个 rootfs 的同一个内核，erofs 支持是现成的（宿主上没有 erofs 工具，
`wsl` 也没装任何发行版）。脚本：`vm/_img_check.sh`，输出：`vm/_imgcheck_a6pro.txt`、
`vm/_imgcheck_a6pro2.txt`。`/ro` 这个 lowerdir 路径在最终根里已经不存在（`/proc/mountinfo`
只剩一条 `0:26 / / overlay`），所以想核镜像原值必须走 `/dev/vda`，不能走 `/ro`。

### 11.2 镜像原值 与 运行态 的差异（a6pro）

| 路径 | 镜像（`/mnt/img`） | 运行态 | 差异来源 |
|---|---|---|---|
| `/usr/bin/miniapp` | 厂商 ELF，5492 B | 232 B shell wrapper | 我们的 `fixup.sh` 首靴改名+替换 |
| `/usr/bin/miniapp.real` | **不存在** | 5492 B | 同一文件的改名，只存在于运行态 |
| `/usr/lib/libfalcon.so` | md5 `9436d914…` | md5 `46629ed5…`，同尺寸 | pack 的等长补丁（`patches/libfalcon.so`） |
| `/oem/…/libs/libyddal_base_nmt.so` | md5 `fb0909d6…` | md5 `6f875586…`，同尺寸 87464 B | 首指令改 `bx lr` 的 NMT 补丁 |
| `/etc/miniapp/resources/cfg.json` | `direction=270`、`bpp=16`，783 B | `direction=0`、`bpp=32`，781 B | `scripts/initramfs-init.sh:341` 按 `patches/cfg.json.overrides` 重写 |
| `/userdisk`、`/userdata` | 空目录 | 20 个二级包、日志、core | 状态盘内容，与固件无关 |
| `/uresource` | 空目录 | 空目录 | 厂商真机上是独立分区挂载点 |
| `/usr/configs/` | **没有** `youdao_hal_audio_config.json` | 同样没有 | a6pro 是 tinyalsa 版 HAL，与 §9 判定一致 |

### 11.3 三条被推翻或补强的结论

1. **今天 §8 把 `miniapp.real` 当成固件里的文件名，是错的**：固件只有一个 `/usr/bin/miniapp`，
   `.real` 是我们的改名。以后描述启动链要写「镜像里的 `/usr/bin/miniapp` → 运行态被拆成
   wrapper + `.real`」。
2. **颜色与显示**：厂商给 a6pro 的 falcon 配置是 `16 bpp(RGB565) + direction 270`，
   我们为了让 VM 的 bochs 平面 1:1 显示，把它改成 `32 bpp + direction 0`。
   R/B 颠倒因此有了一个新的解释位置——它可能不是「RV1106 falcon 天然输出 RGBA」，
   而是**我们把 bpp 从 16 强制成 32 之后** falcon 的字节序与平面格式不再匹配。
   `swap_rb` 目前是在宿主呈现层补救，属于可工作的补丁，但根因层级要按这条重判（待实测：
   保持 `bpp=32`、只调 falcon 的格式键，或反过来验证 16bpp 路径在 VM 里是否可行）。
3. **NMT / 资源缺失的根因是挂载点，不是缺文件**：镜像里
   `/oem/YoudaoDictPen/output/localdict -> /userdisk/uresource/localdict`、
   `localsound -> /userdisk/uresource/localsound` 是**符号链接**，而 VM 没有
   `/userdisk/uresource`，链接悬空 → `loadNmtPatch` 抛 `MiniNmtException`。
   真正的 NMT 模型在镜像里有实体：`/oem/YoudaoDictPen/output/nmt/transformer_{c2e,e2c}`、
   `localres/recording.json`。所以这一族的正解是让 `/userdisk/uresource/{localdict,localsound}`
   存在（空目录即可解悬空，内容再谈），而不是永久给 NMT 打补丁。

### 11.4 顺带确认的一件事：应用包从哪来

镜像里 `/userdisk`、`/userdata` 都是空目录，两个预置包只在
`/etc/miniapp/resources/presetpkgs/`（`8080222437664451` 3 460 690 B、
`8080252464522508` 9 421 188 B）。因此 a6pro 那 20 个二级应用包**不来自固件**，
是这台 VM 历史运行期装上去的（`pkg` 目录 mtime 分三批：10-01 18:50、10-19 13:24、
10-19 21:33；现在 `SecondaryStartup` 报 `need second apps install:(0)`）。
对照组：s6pro 走的是另一条路，包里带 `packs/s6pro/patches/presetpkgs/*.amr`，由我们自己塞。
这条差异会影响「换一台新机器能不能复现同一套应用」的判断，后面要单独核实 a6pro 的下载来源。

## 12. 声音验证（2026-10-22）

### 12.1 首要原因是宿主端点被静音

用 Core Audio 读默认播放端点（脚本 `scripts/audio-endpoint.ps1`，只读时也能用；本机草稿 `vm/_audio_endpoint.ps1` 是同一份）：


客机里 `aplay` 能把音轨完整写完、`peak max = 34.6%`（同一脚本 `-PeakSeconds` 采端点峰值），
说明**链路是通的，声音被宿主这一层静音挡掉了**。取消静音并调到 80% 后同一段音轨可闻。
这条与机型无关，任何一台「没声音」都应当先查它。

### 12.2 a6pro：补第二块声卡不等于修好音量

实验：QEMU 挂两块 `usb-audio`（同一 dsound 后端），客机出现 `card1 [Audio_1]`。

| 项 | 结果 |
|---|---|
| `/proc/asound/cards` | card0、card1 都在 |
| `tinyplay tone.wav -D 0 / -D 1` | 两卡都 `Played 192000 bytes`，无报错 |
| `hal-audio-volume -g` | 仍然 `is_okay=0` |
| 应用日志 `setVolume` | `setVolumeCallBack--->80  is_okay:-19`（`-ENODEV`） |

原因不是卡号：HAL 找的 mixer 控件名是 `DAC LINEOUT Volume` / `Playback Volume`，
而 QEMU 的 USB 声卡只有 `Audio Output Volume Control Playback Volume`（card0/card1 同）。
结论：**a6pro 要修音量，必须解决控件名映射**（改 HAL、或给 libtinyalsa 加一层 name 拦截），
单纯补 card 不够。附带收获：`tinyplay` 在两块卡上都正常，说明 PCM 通路与卡号无关。

### 12.3 x6pro：HAL 落到 card0，应用按键路径还没坐实

- `hal-audio -s 40` → `is_okay=40`，`amixer -c 0 cget numid=3` 由 240 变 153（见 §9.1）。
- 应用侧日志：`[YVolumeAdapter] getVolumeCallBack--->80  is_okay:80`，与设备写入一致。
- 按键注入 `/usr/bin/input-event-handle set 114/115` 返回 0，但 mixer 值不动；
  说明 x6pro 的音量键不走这条 HAL 注入路径（待查：可能只认 evdev 的 fake-keys 设备）。
- 触屏路径另有一条坑：`dpctl tap` 按 960×480 映射，而 x6pro 的有效画面是
  `yoffset=107` 起的 960×266 带，点状态栏要自己加上这段偏移。

### 12.5 a6pro 音量：控件名的判定规则（反汇编结论）

`vm/_arm_dis.py` 解 `libydhal_audio.so.2.0`（ARM32、.text 0x1510–0x522c）得到实际规则：
这个库**不调用** `mixer_get_ctl_by_name`，而是遍历 `mixer_get_num_ctls` / `mixer_get_ctl` /
`mixer_ctl_get_name`，对每个控件名做 `strstr`：

```
必须包含 "Playback Volume"
且包含 "PCM" | "Speaker" | "Headset" | "Headphone" 之一
否则跳过（跳到下一个 ctl）
```

QEMU 声卡的控件名是 `Audio Output Volume Control Playback Volume`：前半命中，
后半四个词一个都不含 → 整张卡被跳过。这就是 `is_okay=0` / `-19` 的由来。

尝试过的补丁：把常量 `PCM` 三个字节改成 `Out`（等长，命中 `Output`），装上并重启后
单卡、双卡（`card1` 也在）两种配置都仍是 `is_okay=0`，
`Do volume control callback exit, ret=35, ctrl_ret=0`，两块卡的 mixer 值都不变。
**结论：名字是必要条件，但不是全部；失败点在更上游**（大概率是按设备类型选 card/ctl，
或那个异步回调里的 35）。补丁已撤回，设备上恢复原库（md5 `61a885c9…`），
补丁样本留在本机 `vm/_audio_patch/`，未使用。

下一步要拿 `ret=35` 的含义与 type→card 的映射，需要继续沿着
`yd_hal_audio_module_new → yd_hal_audio_init` 与 `_volume_control_*` 那条线程读代码。

### 12.6 a6pro 音量：两条路径与一次库层验证

继续读 `libydhal_audio.so.2.0`，把两条路径分开了：

| 设备类型 | 定位方式 | 结果 |
|---|---|---|
| type 0（speaker） | 直接返回硬编码名字 `DAC LINEOUT Volume` 和一个 id（0），不做枚举 | 名字在 QEMU 声卡上不存在 |
| type 1（digital） | 打开 mixer，遍历控件，要求名字含 `Playback Volume` 且含 `PCM`/`Speaker`/`Headset`/`Headphone` | 我们的卡名不含后四个 |

`yd_mixer_set_int_value_by_name_or_id` 的失败码也对上了：按名字查不到控件时返回 `-19`，
应用日志里的 `setVolumeCallBack--->80 is_okay:-19` 就是这条。

**库层拦截已验证可行**：写了一个只导出 `mixer_get_ctl_by_name` 的 preload
（`vm/_audio_patch/vmaudio.c`，zig 交叉编译成 armhf，导入只有 3 个 tinyalsa 接口），
把 `DAC LINEOUT Volume` / `Playback Volume` 别名到名字里含 `Playback Volume` 的那个控件。
用一个故意返回 NULL 的调试版覆盖 `mixer_open`，`tinymix` 立刻打不开 mixer，
说明 uClibc 下 interpose 生效、加载顺序正确。

**但厂商的 `hal-audio-volume` 测试工具在这条路径上根本不调用 `mixer_get_ctl_by_name`**
（preload 加了日志，一次都没打印），它的回调自行返回 `ret=35`、`is_okay=0`。
应用侧是否走到这个名字查找，还差一步验证：我们的 `fixup.sh` 每次启动都会重写
`/usr/bin/miniapp`，所以要把 shim 挂进应用必须改**包里的**
`patches/miniapp-wrapper.sh`（而不是客机上的那份），再整机重启。

重启后应用正常出日志。shim 源码与产物只留在本机 `vm/_audio_patch/`，未进包。

### 12.9 应用放音的真实链路：缺 card1 + SoundPlayer 没起

用「随身听」按用户入口放一集故事，暴露出两个与音量无关的缺口：

1. **SoundPlayer 进程不存在**。x6pro 的 `rcS` 里没有它的入口（a6pro 有
   `guardian_run /usr/bin/runSoundPlayer start`），app 的 `playMedia` 通过 socket 发出去没人消费。
2. **声卡号不对**。手动拉起 SoundPlayer 后仍然放不出声，日志里是
   `ALSA lib pcm_hw.c:(_snd_pcm_hw_open) Invalid value for card` +
   `openOutputDevice faild`——它按 card 序号打开设备，而 VM 只有 `card0`。

补上第二块 `usb-audio` 后同一次点击变成：`open=======success`、
`card1 ... state: RUNNING`、宿主端点峰值 **52.6%**；把这两件事落进包里再冷启动，
峰值 **59.8%**，故事能连续播放。

落地方式：

| 改动 | 位置 | 说明 |
|---|---|---|

### 12.13 x7 应用内播放：两个缺口与修法

### 12.16 s7pro：miniapp 无限重启（已定位并落包）

现象：s7pro 界面正常，但 miniapp 每 16 秒终止并被 guardian 重新拉起，循环不止；
干净启动就能复现（今天 18:00 前累计 400+ 份 `.dmp`）。

**真因：家长控制模块的定时器在 asio 线程上抛未捕获异常。**

```
asio_for_timer 线程
  YTimerPrivate::startTimer(int)                 libyddal_base_core.so
   → YParentControlPrivate::connectServer()      libbusiness_parentcontrol_696588962.so
     → YAWebSocketEngine::sendLoginMsg()         同上
       → YAWebSocketEnginePrivate::sendMsgContent()  同上
         → YWebSocket::sendTextMessage()         libyddal_base.so
           → yd_base_websocketpp::exception::~exception()   ← 正在展开这个异常
```

厂商日志里这条循环的原文（前一轮从 `DictPen_*.log` 抓到的）是
`terminate called after throwing an instance of 'yd_base_websocketpp::exception'` +
`terminate called recursively`，紧跟 `Aborted`。家长控制（时长管理）每 10 秒要连一次
云端 WebSocket，VM 里连不上，`sendTextMessage` 在连接未 open 时抛 websocketpp 自家异常，
那条线程上没有 catch，于是 `std::terminate` → `abort`。

| 项 | 实测 |
|---|---|
| 定时器周期 | 桩里计数：每 10 s 进一次 `connectServer`；崩溃发生在其后约 6 s |
| 抛出模块 | `libbusiness_parentcontrol_696588962.so`（包 `8001671616562847`） |
| 线程 | `asio_for_timer`（`libyddal_base_core.so` 里的 asio scheduler 线程名） |
| 转储 | `/userdisk/corefile/4.23.0/miniapp.real-*.dmp`，每 16 秒一份 |

**之前写在这里的结论有两条是错的，一并作废：**

- 错一：「本地录音 WebSocket `ws://127.0.0.1:9307`（服务端 SoundRecord）被掐断」。
  反证：杀掉 SoundRecord 让 9307 没人监听，崩溃节奏不变；崩溃栈里也没有任何
  SoundRecord/9307 相关帧。走 WS 的是家长控制，连的是云端。
- 错二：「缺麦克风是原因之一」。反证：加载 `snd-aloop.ko` 造出 card3（`pcm0c` 齐全），
  同时把 HAL 的 `Y08_CV1813_V0.mic_card_id` 改成 3、把 `/etc/asound.conf` 的采集别名
  `softvol_cap` 与 `adc_dsnooper` 从 `hw:0,0` 改指 `hw:3,0`，并用
  `arecord -D default -d 1 -f S16_LE -r 48000 -c 2` 实测写出 192044 B —— 采集通了，
  崩溃照旧。这些实验改动已全部撤销（配置还原、`rmmod`、重启后只剩 3 张 usb-audio 卡）。

**栈是怎么抓到的（可复用）**：`__cxa_throw` 抢不到（厂商把 C++ 运行时静态链接进了各家
库，客机 maps 里没有 `libstdc++.so`），SIGABRT 处理抢不过厂商自己装的，ARM32 上
`backtrace()` 出来的全是 `libc backtrace+0x37` 自环。可行的一条：interpose `abort()`，
在里面**线性扫栈**，把落在 exec 段里的字都打出来（`vaddr = w - map_lo + map_off`，
只取 `/proc/self/maps` 里 `x` 且路径以 `/` 开头的段），宿主侧再用 pyelftools 按
`.dynsym`/`.symtab` 解析。工具：`vm/_s7_crash/catch4.c`、`vm/_s7_crash/resolve.py`、
证据 `vm/_s7_crash/scan.log`（编译器 `vm/_zig/zig-windows-x86_64-0.13.0`）。

**落包修法**：`packs/s7pro/patches/libvmappfix-armhf.so`（源码
`packs/s7pro/patches/appfix.c`，zig 编 armhf，桩掉 `YParentControlPrivate::connectServer`；
同一个库里还带 §12.17 的 `verifyLicense` 恒真），
由 fixup.sh 第 11 节装进 `/usr/lib`，`miniapp-wrapper.sh` 的 `LD_PRELOAD` 追加它。
符号是 `.dynsym` 里的 `STB_GLOBAL`、库没有 `-Bsymbolic`，所以 interposition 生效
（桩里第一条日志实测到 `self=0xecb380e0`）。

**验证**：`down` + `up --pack s7pro` 干净重启后，首页截图 `vm/_s7_stable_home.png`
正常，miniapp pid 145 s 不变，`.dmp` 计数不变，`/proc/<pid>/maps` 里能看到桩被加载。
代价：家长控制（时长管理）在 VM 里不再连云端，它的同步与限额界面不可信。

| 下拉快捷面板把音量条点到 38% | 97 [38%] | RUNNING（播放没断） | 37.7% |

`mediaPlayerManager` 那条 `TypeError: not a function`（首页包 `8080222437664451`）
在能出声的情况下仍然每 30~60 秒出现，**与放音无关**，是另一件事，没继续追。

**这轮真正留下的东西**：控制台声音页原来把读写都写死在 `-c 0`，在输出设备不是 card0 的
机型上显示的就不是笔里那颗控件。已改成按包声明：`[audio].volume_card` →
`harness.volume_card()`（没声明按 card0，超出 `[audio].cards` 收到最大合法卡号），
声音页的读/写/静音/改完复读四处都用它；s7pro 声明 `volume_card = 2`。
合成点击进不了控制台窗口，所以验的是控制台自己那条代码路径：
`python vm/_snd_card_check.py s7pro` 得到 `{'card': 'Audio_2', 'vol': 80}`，
与笔里滑杆同一个值（改之前读 card0 显示 94%，两边不一致）。

**逐台测音量的正确顺序**（这次学到的）：① 先定输出卡 —— `cat /tmp/headSetStatus`
与 HAL 段里的 `digital_hs_card_id`/`speaker_card_id`，或直接 `amixer -c N sget` 逐个看谁在动；
② 播放判据用 `pcm0p/sub0/status` 的 `RUNNING` + 宿主端点峰值，不要只看应用日志；
③ 召出控制条再按播放（几秒自动收起）；④ 测试音放 `/userdata`，那台上 `/tmp` 会被清掉；
⑤ `/usr/configs/youdao_hal_audio_config.json` 会被厂商服务**在运行中回写**（实测：手改回
固件原值之后，一个没重启的 `runSysconfigMgr` 把内存里的旧值写回了文件）。所以这台上手改
配置不稳定，要改就走包的 `[adapt.replace]`（S00replace 在 rcS 早期每靴覆盖），
并且改完要重启整机或至少重启那个服务才算数。

### 12.19 点云端专辑曲目就崩：`std::stoll("")`，数据来自云端

现象：随身听 → 听力精选 → 双语推荐 → 任一专辑 → **点曲目标题或点下载图标**，约 1 秒后
miniapp abort（实测连崩三次，`.dmp` 427/428/429）。本地导入的曲目不受影响（§12.18 能正常播）。

机制（探针实测，不是推测）：`libbusiness_listening.so` 的 `YColumnAudioListModuleImp::loadMedia`
→ `YYdListenDbQueryPrivate::loadColumnItem` 回调里调用 `std::stoll`，参数是**空串**：

```
strtoll t=1792675657.602 [threadpool_2] base=10 arg=""
terminate called after throwing an instance of 'std::invalid_argument'
```

抛在厂商自己的线程池线程上，没人 catch → `std::terminate` → abort。

抓法（比上一轮的扫栈更省）：`std::stoi/stoll` 在厂商静态链接的 libstdc++ 里，抢不到；
但它最终调 glibc 的 `strtol`/`strtoll`，那是**动态符号**。preload 这两个函数、只在
`*endptr == nptr`（一个数字都没解析出来，正是标准库抛 `invalid_argument` 的条件）时打一行
输入串与线程名，就拿到了上面的证据。探针：`vm/_s7_crash/strcatch.c`
（`zig cc -target arm-linux-gnueabihf -shared -fPIC -O1`），挂法同 §12.16 的 wrapper。
空闲时零噪声，所以不用做去重。

崩的那本书云端报文（`syncHttpGetYdTextBookContent`，书 key `B_AA3118BC9C2847D984701E36EA84587A`
= 安徒生童话选集）里，走的是**教材通道**：`source=interTextbook`、`source_data_type=textbook`，
而 `part_content` 是 `{"fragment_path_for_53":"","end_page":-1,"start_page":-1,
"first_sentence":"","title":""}` —— 页面字段是 `-1`（数字，不是空串），
所以喂给 `stoll` 的是某个字符串字段被当数字解析。本机 `listening.db` 里 52 条曲目
全部 `download_state=0`、`media_file_size=0`（只同步了元数据，没下过内容）。

**已实测 / 待证**：

- 已实测：崩溃点、空串、线程、复现三次、本地导入不受影响、教材类与非教材类专辑都崩
  （双语推荐里的 Mr.English 与安徒生童话都崩）。
- 待证：**这是厂商 bug 还是这台 VM 触发的**。报文来自云端、字段内容与设备无关的样子，
  倾向于是厂商在「教材通道里的非页面书」上的 bug（真机同样会崩）；但没在真机上验过，
  也没在第二台 VM 上跑过同一本书。判据：另一台机型点同一本书，看是否同样
  `strtoll ... arg=""` + abort；或拿真机点一次。
- 未做：learningCenter 包（`8001670662488112`）本机 `amrs/` 里没有，客机也装不了
  （`miniapp_cli install` 只吃本地 .amr），日志里的 `Can't spy : tag is not found:learningTrack`
  与 `startService(... learningCenter) package not found` 是另一条独立缺口。

#### 12.19.1 第二轮：崩点精确到指令，且**改数据库没用**

在 `stoll` 那一步加栈扫描后（`vm/_s7_crash/strcatch.c`，同时装 SIGSEGV 处理），拿到：

```
strtoll ... [threadpool_1] arg=""
  sp+27  libbusiness_listening.so+0x7610c      ← 调用者的返回地址
SIGSEGV ... addr=0xeb7fe000                    ← 同一根因在展开路径上的表现
```

反汇编 `0x76000–0x76170`（`vm/_s7_crash/dis_arm32.py`，GNU PIC 的 `ldr r1,[pc,#imm]`＋`add r1,pc,r1`
模式解析字符串）看清这个映射函数按顺序读四列：
**`media_info`、`download_state`、`download_time`、`task_id`**；`0x76108` 那条 `bl` 对应
**`task_id`**，返回地址正是 `0x7610c`。

**关键否证**：我把 `table_media_download_list` 的 `task_id` 从空串改成 `'0'`，并装了一个
`AFTER INSERT` 触发器（空就补 `'0'`），重启后点同一首**照样崩在同一行指令**。所以空串不是
库里存的值 —— 是这个映射器**要的列在结果集里根本不存在**（`getValue("task_id")` 返回 NULL →
字符串保持空 → `stoll("")`）。`table_listen_media` 的列里确实没有 `task_id`/`media_info`，
而这个 mapper 是「下载列表」形状（四列同 `table_media_download_list`）——**查询与映射器对不上，
是应用侧的问题，VM 这边改数据改不掉**。

顺带确认的 VM 差异（不是这次抛异常的原因）：下载任务路径还会跑
`cat /sys/block/mmcblk0/size`，这台的块设备只有 `vda`/`vdb`（`/sys/block` 里没有 mmc），
命令报 `No such file`；`libbusiness_listening` 的 `runTask` 在这种行上会留下 `task_id=''` 的记录。
preload 里伪造这个尺寸（`vm/_s7_crash/fakemmc.c`）没被调用到，说明那条命令不出自
miniapp 进程的 `popen/system`。

**能走的三条路**（要人定）：① 把 `0x76108` 这条 `bl` 改成「空串当 0」的字节补丁，随包在
开机钩子里打（代价：绑死这个 app 版本，应用更新后偏移得重找，重装 app 会冲掉）；
② 拿一台真机（或配套版本）的 `listening.db` 与 app 包，比对这台的查询/映射器是否本来就该一致；
③ 接受为已知限制，只保证本地导入曲目可播。

本轮实验痕迹已还原：`vm_fix_task_id` 触发器删除、`table_media_download_list` 的测试行删除、
探针库与日志删除、wrapper 回到两条包内库。
